# 可灵批量图生视频（做真动画 MV 的执行流程）

首帧图已就位、要出「角色真的在动」的镜头时走这条。路线选择见 `配图路线选择.md`；提示词质量门禁见 skill `kling-prompt-quality-gate`。

## 一、凭据从哪读

**Key 不在项目的 `.env` 里，在 systemd service 文件里：**

```bash
grep -i kling /etc/systemd/system/linghu.service
# Environment=KLING_185_ACCESS_KEY=...   ← 只用 185 这套，另一套已废弃
# Environment=KLING_185_SECRET_KEY=...
```

找不到时依次查：`/etc/systemd/system/*.service` → 项目 `.env.keys` / `.env.example`（那里的通常是废弃的旧账号）。

## 二、鉴权：JWT HS256

```python
def b64u(d): return base64.urlsafe_b64encode(d).decode().rstrip('=')
h = b64u(json.dumps({"alg":"HS256","typ":"JWT"}).encode())
now = int(time.time())
p = b64u(json.dumps({"iss":AK,"exp":now+1800,"nbf":now-5}).encode())
s = b64u(hmac.new(SK.encode(), f"{h}.{p}".encode(), hashlib.sha256).digest())
token = f"{h}.{p}.{s}"   # 请求头 Authorization: Bearer <token>
```

JWT 有效期 30 分钟，**批量任务要缓存并复用**（`exp` 前 5 分钟刷新），不要每次请求重算。

**鉴权是否通的判法**：`401` = key 错；返回业务错误码（如 `1203` 模型已停用）= key 对、参数或模型名不对。

## 三、建任务

`POST https://api-beijing.klingai.com/v1/videos/omni-video`

```json
{
  "model_name": "kling-v3-omni",
  "prompt": "Maintain the ... style of the reference image exactly. <动作 + 运镜 + 光>",
  "duration": 5,
  "mode": "std",
  "aspect_ratio": "9:16",
  "sound": "off",
  "first_frame": {"base64": "data:image/png;base64,<...>"}
}
```

- `duration` 只接受 **5 或 10**。镜头需要 11 秒时生成 10 秒再慢放补足。
- `mode`：`std` = 720p，`pro` = 1080p（贵一倍）。用户要「饱满」「不要小气」时用 pro。
- `sound` 必须 `off` —— 音频用自己的混音，可灵出的声音会打架。
- `first_frame.base64` 要带完整 data URI 前缀（和 ACE-Step 返回的相反：**这里是我们要加前缀**）。
- `kling-v2-1` 等旧模型已停用，走 `/v1/videos/image2video` 会返回 `1203`。

### 实测通过的简版结构（只要一两张参考图时用这个）

```json
{"model_name":"kling-v3-omni",
 "image":"<纯 base64，不带 data: 前缀>",
 "prompt":"...",
 "mode":"pro", "duration":"5", "aspect_ratio":"9:16", "cfg_scale":0.7}
```

比 `first_frame:{"base64":"data:..."}` 少一层嵌套，实测同样可跑，且 `mode:pro` + `aspect_ratio:9:16` 直接出 **1080×1920** 竖屏（不用再 scale），单镜 81–203 秒、6.8–9.9MB。

## 三之二、先调这两个参数，再谈别的（决定「动不动」）

### ① `cfg_scale` 是动作幅度开关：0.3 会把画面压成静止

同一张首帧、同一段提示词，只改 `cfg_scale`：

| cfg_scale | 结果 | 评分 |
|---|---|---|
| **0.3** | 人物几乎不动、背景完全静止，画面清晰但像定格照 | 5/10 |
| **0.7** | 抬手、转身、躯干扭转，尘埃飘动，脸仍不崩 | **9/10** |

低 cfg 看起来「稳」，实际是把动作压掉了 —— 而「动」正是这条路唯一值钱的东西。**默认从 0.7 起调**，需要更激烈再往上试，不要因为怕崩就往低处调。

### ② 提示词只写「他做了什么动作」，禁止写构图

这是本地与云端模型都会踩的同一个坑：**写画面长什么样，输出就是静态图；写身体在做什么，才有运动。**

| 写法 | 例 | 结果 |
|---|---|---|
| ❌ 构图式 | `Over-the-shoulder framing: blurred worker shoulders in the foreground, the foreman in three-quarter profile facing frame left, a crane behind` | 静止 |
| ✅ 动作式 | `The foreman TURNS his head toward the man beside him, RAISES his free hand and jabs a finger in the air, his torso twisting with the gesture; the other man shifts his weight and turns his shoulder` | 真动 |

三条硬规则：

1. **每条提示词至少 3 个明确的身体动作动词**（turns / raises / shifts / leans / twists / swallows / exhales），不要用 look / hold / sit 这类静态动词。
2. **背景也要给动作**（`the crane swings across the sky`, `dust blows across the court`, `neon slides across his face`），否则人物动了背景还是死的，一眼假。
3. **风格/画风已在首帧里，不要再描述构图和人物长相** —— 那些挤掉了动作词的预算，还把模型往「复刻这张照片」的方向推。

## 四、查余额 / 扣费明细

**只有这一个接口能用：**

```
POST /account/billing/package            ← 注意没有 /v1 前缀
body: {"start_time": <ms>, "end_time": <ms>, "limit": 500}
```

`/v1/account/balance`、`/v1/user/balance`、`/v1/account/info`、`/v1/resources/packages` **全是 404** —— 不要在这上面反复试，直接去翻 `kling.ai/document-api/api/assets/billing-deduction/package`。

返回每条扣费的 `unit_before_deduction` / `deduction_amount` / `unit_after_deduction`，**最新一条的 `unit_after_deduction` 就是当前余额**。

实测计费（kling-v3-omni / std / 720p）：**0.6 单位/秒，5 秒镜 = 3.0 单位，10 秒镜 = 6.0 单位**。19 镜混合 5/10 秒（共 135 秒）实测扣 81 单位。

## 五、批量提交（并发）

单个镜头实测 **约 200 秒（3.3 分钟）**。19 镜串行要 1 小时以上，**必须并发**。

- 资源包是 20 并发，实际用 **6 个线程**提交足够稳（被限流就退避重试 429/500/502/503）
- 19 镜提交本身约 1 分钟
- 提交完立刻把 `{tag: task_id}` 落盘 JSON —— 脚本挂了能续

轮询：`GET /v1/videos/omni-video/{task_id}`，15 秒一次，读 `data.task_status`：

- `succeed` → `data.task_result.videos[0].url`，下载到本地
- `failed` → `data.task_result.err_msg`
- 其他 → 继续等

实测 6 并发下 19 镜从提交到全部下载完 **约 84 秒**（大批任务本来就接近同时完成）。

## 六、装配（关键：源片时长 ≠ 镜头时长）

```
可灵 720p/1080p → trim 或慢放补足 → scale 到 1080×1920 → fps 30 → yuv420p → concat → 烧字幕 → 混音
```

每镜三种情况：

| 情况 | 处理 |
|---|---|
| 源片够长 | `trim=0:<需要时长>,setpts=PTS-STARTPTS` |
| 源片略短（差 10% 内） | `setpts=(源长/需要长)*PTS` 慢放，音高不变 |
| 源片明显短 | 慢放最多到 0.55x，仍不够就再 `tpad=stop_mode=clone` 定格末帧补 |

统一过一遍 `scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920`，720p 拉上来在抖音压缩后看不出差别。

拼完再确认一遍总时长与音频完全一致（逐镜时长相加要对得上，误差 >0.12 秒会有音画渐进错位）。

## 七、坑

1. **`opener.open()` 不接受 `context=` 关键字。** 要绕系统代理 + 忽略证书时，context 必须挂在 handler 上：
   ```python
   OP = urllib.request.build_opener(
       urllib.request.ProxyHandler({}),
       urllib.request.HTTPSHandler(context=ctx))
   OP.open(req, timeout=90)     # 不要再传 context
   ```
   直接 `OP.open(req, context=ctx)` 会 `TypeError: got an unexpected keyword argument 'context'`。
2. **系统代理会拦 API 请求。** 调用前 `unset https_proxy http_proxy`，或按上面用空 `ProxyHandler`。
3. **先跑 1 镜再放量。** 单镜验证成本 3 单位，能在花 80 单位之前发现风格漂移／脸崩／口型问题。
4. **不要口型时把「不张嘴」写死**：`open mouth, teeth showing, smiling`。**但需要口型时不要放弃** —— 可灵 `/v1/videos/lip-sync` 实测可用（详见下节），卡通人物张嘴说话自然、脸不崩。这一步以前被判定「必崩」，是没有走 lip-sync 接口只靠图生视频提示词硬凑的结论。
5. **衣服颜色偶尔会飘**（同一角色跨镜从深黑变浅灰）。不影响叙事，不要为这个重跑整批。
6. **10 秒是硬上限**，需要更长的镜头就慢放或拆成两个角度，不要指望加参数。

## 八、对口型（lip-sync）：静态人物真的张嘴说话

**结论先说：可用。** 实测卡通人物口型开合自然、有说话感、脸不崩、跨帧一致，画风也守得住。以前认为「必崩」是只用图生视频提示词硬凑的结果，不是这个接口的能力。

### 三步链路

```
FLUX 出人物图 → omni-video 出 5 秒微动视频 → lip-sync 用音频驱动口型
```

### 参数（实测提交成功的唯一结构）

```
POST /v1/videos/lip-sync
{
  "model_name": "kling-v3",
  "input": {
    "mode": "audio2video",
    "video_id": "<omni-video 返回的 id>",
    "audio_type": "file",
    "audio_file": "data:audio/mpeg;base64,<音频 base64>"
  }
}
```

`video_id` 与 `video_url` 二选一，**优先 `video_id`** —— 省掉「先把成片下载下来再找托管」这一步，实测直接出片。

| 字段 | 允许值 | 坑 |
|---|---|---|
| `mode` | **只有** `text2video` / `audio2video` | 试 image/video/t2v/lip 全 400，错误信息才列出允许值 |
| `video_url` / `video_id` | **两种模式都必填** | `text2video` 也要视频，它不是「文本生成视频」而是「用文本指令改视频」 |
| `audio_type` | **只有** `file` / `url` | 传 `base64` 报 400 |
| `audio_file` | **吃 base64**（data URI 或纯 base64 都行） | ⭐ 关键 —— 不需要公网托管音频，本地文件直接塞 |

**`audio_type:"file"` 配 `audio_file:<base64>` 是唯一不需要上传服务就能跑通的组合。** 不要因为字段叫 file 就去找上传接口 —— 可灵没有上传接口（`/v1/upload`、`/v1/files/*` 全是 404）。

### 查任务

```
GET /v1/videos/lip-sync/{task_id}
→ data.task_status: submitted / processing / succeed / failed
→ data.task_result.videos[0].url
```

### 什么时候用

**不要全程口型。** 一部 5 分钟的片子每 5 秒都对口型 = 60+ 个片段、400 单位、40 分钟。爆款原作也不是全程：**只在人物开口的关键句对口型，其余用静态图运镜填。**

每位主角 2 个口型镜头（段首最狠那句 + 段尾回扣那句）就够撑住「他在唱」的感觉，覆盖全片约 25% 时长。

### 音频切片要按实际时间轴

口型镜头用的音频必须是从该段成品音频里按 `-ss <段内起点> -t <时长>` 切出来的纯净人声段，不要用原始 TTS 输出 —— 时间轴对不上会导致口型与画面错位。

### 失败不扣费

`task_status: failed` 不消耗单位（实测多次失败后余量未变）。所以可以放心先跑验证镜头。

### image2video 不认 kling-v3-omni

`POST /v1/videos/image2video` 传 `model_name: "kling-v3-omni"` 返回 `1201 model is not supported`。图生视频统一走 `omni-video` + `first_frame`，只有 `lip-sync` 用独立端点。

### 输出自带音轨、时长略短 —— 但时间轴是 1:1，不要拉伸

- 输出 **1264×720、约 6.3 Mbps、自带 AAC 128k 音轨**，时长比输入**略短**（10.03 秒输入 → 9.97 秒输出）。
- **短的那 0.07 秒是末尾切掉的，不是把整段压缩了。** 实测验证：取输出音轨与原曲做互相关，在 0.2/2/4/6/8/9.3/9.7 秒七个采样点上，偏移恒定在 **−0.020 秒**（不随时长增长）→ 时间映射 1:1，零漂移。
- 所以**不要 setpts 拉伸**。拉伸会把一个本来正确的片段人为改成音画错位，并且误差会随段数累积。
- **每段只能放在它自己的音频起点上。** 挪位、拼接顺序调整、借用隔壁镜头的富余时长，都会让嘴型和母版音轨错开（错开量 = 挪动量）。
- 装配规则：①**只用它的画面**（`-an`），音轨一律用母版原曲——每段各编一次 AAC 再接会跳电平、起点各有几十毫秒偏移；②按它的起点定位，只做**尾部裁切**，不做拉伸；③那 −0.020 秒是恒定小偏差，低于口型感知阈（约 40–80 ms），可直接忽略，不要为它加延时滤镜。
- 单段耗时约 **170 秒**，不是秒级。报工时按这个算，别按视频长度算。

#### 一分钟验法：判断重定时是「压缩」还是「切尾」

任何来源的重定时／重编码视频（不只可灵），装配前先测一次再决定要不要对齐：

```bash
ffmpeg -y -loglevel error -i clip.mp4 -ac 1 -ar 8000 -f wav /tmp/o.wav
ffmpeg -y -loglevel error -ss <源起点> -t <源时长> -i song.mp3 -ac 1 -ar 8000 -f wav /tmp/r.wav
# 用带 numpy 的 venv（如 /root/venvs/music）跑：取 0.4s 窗口互相关，报输出 t 对应原曲的偏移
```

判据：**偏移恒定 = 整体平移（切尾或加头），可原样放到源起点、必要时整体加一个固定延时；偏移随 t 线性增长 = 被压缩／拉伸**，此时才需要按比例 setpts 回拉。不测就假设「必然漂移」会做出多余且有害的拉伸。

### 窗口比片段长时：同一 video_id 再对口型一次，不要重新生成视频

各镜时间窗由歌词长短决定（6–16 秒不等），而单段输出固定约 9.97 秒，所以必然有镜头「窗口 > 片段」。

**正确解法：把缺口那段音频从切点起再喂一次同一个 `video_id`。** 画面复用、嘴型对的是它实际播出位置的那句词，成本只是再一次 lip-sync 调用（且失败不扣费），远低于重生成视频。

两条硬规则：

1. **切点落在 SRT 的句末或句间空档**，一刀都不许切在字中间。窗口超长时优先找「上一句刚唱完、下一句还没起」的位置切。
2. **不许用慢放／定格去凑时长**：慢放会改变嘴型速度，等于把口型改错；定格只能用在**没人唱的空档**（含片尾收尾），因为那段时间本来就该闭嘴。

窗口比片段短时处理最简单：直接裁尾，尾部的 3–5 秒富余全部丢掉，这部分冗余是免费的。先用 SRT 把所有窗口和片段时长列成表算一遍差，再决定哪几镜需要二次对口型 —— 不要等装配时才发现时长对不上。

结论先算，再动手；把「需二次对口型的镜头清单」在批量生成前就定下来，跟视频一起提交。

### 它会自己判断「有没有人在唱」（实测对照）

同一个 `video_id` 喂两段音频的对照结果：

| 输入 | 嘴型表现 |
|---|---|
| 纯人声（demucs `vocals`） | 张合明显，跟语音节奏一致 |
| 纯伴奏（`no_vocals`，完全无人声） | 嘴基本不动，只有眉眼轻微变化 |

三条可直接用的结论：

- **不需要先分离人声**：整轨原曲（人声+伴奏一起）喂进去也能对上，人声在混音里占主导就够它抓。
- **不需要歌词文本**：它只吃波形。歌词只用于最后烧字幕。
- 镜头时间窗内本来没人唱（间奏、空档）时它会自己闭嘴 —— 不用手动去对齐「谁唱谁不唱」。

### 下载结果用 curl，不要用 urlretrieve

7.8MB 的成片用 `urllib.request.urlretrieve` 会抛 `ContentTooShortError: got only 6273759 out of 7837346 bytes`（文件写了一半也算失败）。改用 `curl -sL --retry 3 -o out.mp4 <url>`。

## 九、另一条端点：`image2video` + `model_name: kling-v3`

`omni-video` 是带关键帧/多素材的那条；**只要一张首帧图 + 一段提示词时，`/v1/videos/image2video` 配 `model_name: "kling-v3"` 也能跑通**（只有 `kling-v3-omni` 会返回 1201）。它更简单：没有 `aspect_ratio` 参数，**输出比例跟着输入图走**（16:9 的 1344×768 首帧 → 出 1268×724）。

```json
{"model_name": "kling-v3",
 "image": "<纯 base64，不带 data: 前缀>",
 "prompt": "Maintain the photographic realism and the exact face of the reference image. <动作 + 一种运镜 + 光>",
 "duration": "10",
 "mode": "std",
 "cfg_scale": 0.5}
```

- `duration` 是**字符串** `"5"` / `"10"`，超过 10 秒的分镜必须拆
- 轮询 `GET /v1/videos/image2video/{task_id}`，`data.task_result.videos[0]` 里同时给 `id` 和 `url` —— **这个 `id` 就是 lip-sync 要的 `video_id`，落盘**
- 15 镜串行实测 15/15 成功，单镜约 7 分钟（含轮询），输出 3.7–9.4MB、1268×724、10.04 秒
- 串行不用管并发限制；要压时间就按第五节开线程（20 并发额度，用 6 个足够）
