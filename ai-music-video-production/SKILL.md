# AI 音乐 MV 制作（漫画风·静帧 + 运镜）

> 用于「给这首歌配个 MV」「做成动画／漫画 MV」「出一条竖屏音乐视频」这类请求。
> 分工：歌由 `local-music-generation` 出；本 skill 管拿到音频之后到成片的全部环节。

## When to Use

用户要把一首歌（自己生成的或已有的）做成带画面的 MV、要求「漫画风／动画风」、要做竖屏短视频音乐视频，或要「蹭某个爆款 MV 的形式做一个」。

## 第零道门：先定「演唱型」还是「氛围型」，再谈任何风格

这是整类任务里最容易做反的一步，做反了后面每一镜全废。

| | 演唱型（开唱型） | 氛围型 |
|---|---|---|
| 观众看什么 | **一个人的脸和嘴，在真唱** | 环境、物件、字幕、情绪 |
| 画幅 | 竖屏 9:16 | 横竖都行 |
| 景别 | 半身/胸像，脸占 25–35%（live 感）到 60–70%（怼脸）|
| 谁在动 | 人的头、表情、口型 | 静帧推拉、空镜、转场 |
| 对口型 | 全程要 | 不需要 |

**判据在用户嘴里，不在播放数据里。** 用户说「我喜欢演唱的」「要看他唱」「有气势」「像明星一样一直唱不同的歌」→ 演唱型，不要再拿“静态推拉 + 硬字幕”的方案去交。说「要氛围」「像 PPT 一样飘」「清淡一点」才走氛围型。

**不要用竞品数据反推用户想要哪一种。** 实测同一批 B 站 MV：740 万播放那条是**零角色的文字排版**、137 万是插画 + 硬字幕、真正“电影感多场景”那条只有 2 万。数据能说明“哪种形态成本低、供给多”，**不能说明这个用户要看什么**。先判形态、再拿数据谈成本，顺序颠倒就是白做一版。

**调研本身也有纪律：样本 < 20 不许下“这类没人这么做”的全局否定结论。** 一次只看 7 个就断言“平台上没人靠音频驱动做 MV”，被用户一句“怎么可能呢，很多画布都这么做”当场推翻；全量重扫 31 个后真实比例是完全相反。同一个平台的作品列表每页只有 20 条，**必须翻到底再统计**；判“有没有对口型”只认画布快照里的硬字段（每个视频节点的 `audioList`、模型名、切片时长），不要看标题猜。

两条路的工艺完全不同（音频驱动数字人 vs 图/文生视频），接口与验收见 skill `kling-lipsync-mv-assembly` 的「入口闸门 0」。

### 生产通道：默认 LibTV，但用户一说「本机 / 本地 Flux3」就立刻切过去

出图、出视频、建画布默认在 **LibTV 平台**做（MCP + 画布），平台有现成的提示词生态可学。开工前先读技能 `libtv` 的两个参考档（在 libtv 技能目录下，不在本技能里）：`14_演唱型对口型画布实测`、`15_场景提示词写法`。

**但这不是一条“永不得用本机”的铁律，遇到下面两种情况立刻换本机 ComfyUI-flux3（`/opt/ComfyUI-flux3`，`127.0.0.1:8191`，GPU1）：**

1. **用户直接要求**（“重新用本地的去生”“用本地的 Flux3 出这八个人”）。他要的是快看到编号卡，不在乎在哪台机器出的。
2. **LibTV 拿不到产物**：任务报 SUCCEEDED，但 `browse_project_media` 返回 `MEDIA_NOT_AVAILABLE`、机位/物件节点 0 个 url。等下去只是浪费他的时间。

本机出人像的两条硬要求（不做就是一轮白干）：**只写看得见的骨相/眼型/鼻唇/皮肤/发质**（写“清冷、克制、有距离感”这类气质词会八张一个模子）；**每轮都做成带大号数字的联系表交给他报号**，被 pass 的整批挪进 `.trash/`，编号跨批不重号。完整纪律见技能 `mv-film-timeline-subtitle-qa` 的「抽卡制」一节，拼板命令见 `comfyui-flux-portrait-generation` 第 5 步。

本机仍不管这些：字幕、字卡、时间轴拼接、烧录（本地 ffmpeg + ASS）、口型（用户明确否决过本机 lipsync：“对出来很飘、很丑”，只用 ±5 帧时间轴微调）。

### 「一人一整段」是演唱型的标准规格，不是一句一镜

扒全量画布后的实测结论（标杆作品约 100 万赞）：

| 项 | 值 |
|---|---|
| 音频段数 | 全曲 ~4:40 只用 **18 段**；主力段 **28–30 秒不切**，短段 7 秒，副歌 15–30 秒 |
| 视频节点 | 38 个 → **每段音频平均配 2 个视频节点**（单次生成出不了 30 秒，必须分段再拼） |
| 贯穿道具 | **立式麦克风**（每人面前同一支麦 = 同一个舞台的证明） |
| 场景 | 全片 **1 个** |
| 口型驱动 | 一句一片音频 → 挂到视频节点（`referenceAudioNodes`），**不是喂整段混音** |

反推的纪律：**少切镜（一个人唱够 28–30 秒）、加一件贯穿道具、场景压到一个**。按“一句一镜”排演唱段是反的——零碎切割会同时毁掉“他一直在唱”和成本。

### 录音棚单场景：演唱型里最省的一种结构

用户在录音棚一个场景里拍、靠室内运镜 + 花絮，问“是不是更省钱更快”时，答案是**省在资产与重跑，不在生成费**——计费按生成秒数×单价，不按镜数也不按场景数。

| 项 | 多场景叙事 | 录音棚单场景 |
|---|---|---|
| 场景资产 | 12–20 张场景图 | 1 张场景母版 + 1 张定妆 |
| 提示词 | 每镜重写环境 | 只改「机位 + 动作 + 这一句唱什么」 |
| 废片 | 换背景就漂脸 | 参考图固定，脸几乎不漂 |
| 出片 | 15 镜 ≈ 40 分钟 | 8–10 镜 ≈ 20–25 分钟 |

机位只留 5 个：**A** 中近景正面（麦在画面右侧 1/3，占 45%）/ **B** 侧 45° 近景过防喷罩（副歌、口型最清楚）/ **C** 过肩、前景调音台虚化（2–3s 垫空）/ **D** 低角度仰拍（情绪高点）/ **E** 手持微晃（花絮感）。机位之间用**遮挡切**（人走过麦架、手挡镜头、身体出画），不要硬切。

花絮镜 4–6 个、每个 2–3s、**不挂音频也不对口型**、复用同一张场景图：手指推推子 / 耳机摘下挂脖子 / 歌词纸划掉一行 / 保温杯拧开冒气 / 隔断外助理比手势 / 唱错一句笑着摇头。它们干两件事：给长镜做呼吸、让观众相信这是真录音棚。

三条纪律：

- **单镜 12–15 秒为上限，不要真上 28–30 秒。** 长镜口型会漂；「一人一整段」的观感要用「同机位连续 + 遮挡切」把 2–3 个 15 秒接出来
- 一条线里只有一个人张嘴，每镜都写死
- **模型会自己重生成一轨声音，不用你喂的切片**（实测：喂 9.7s 纯人声，出片自带音轨 10.08s，与切片包络相关只有 0.24）。成片必须 `-an` 静音贴原曲母版；也**不能拿自带音轨验收口型**，只能抽帧看嘴形或本地 LatentSync 兜底

运镜幅度：10 秒推到「只剩鼻子和嘴」是过头，推镜目标停在**胸上景 → 头肩**。

**棚里两件必有的道具：头戴监听耳机（挂麦架上 / 挂脖子上）+ 调音台上的监看屏**（显示抽象波形，不出可读文字）。耳机是「真在录音而不是在对口型」最快被认出的信号，双手也能空出来做动作；屏幕本身就是花絮容器——把回放画面 / 波形 / 刚唱错的那一条做成画中画塞进去，**本地合成 0 生成成本**。

**要持续接歌，资产必须按编号管**（否则第二天就分不清哪条音频是哪版）：`CH-M01-短发硬朗-36` / `SET-01-小型私人棚` / `SET01-CAMA-SH03` / `SONG-<歌名>-V02` / `<歌名>_V02_CH-M01_SET01-CAMA-SH03_r1.mp4`。一歌多版排产（多版试听→定版→demucs→切片→男声女声各录→合并成 12–15s 镜→静音贴原曲）、8 条运镜库与节奏公式、选角定角判据、平台丢节点的处理，全部在 `references/录音棚批量录制与运镜库.md`。

**同一版录两个歌手时，棚 / 机位 / 运镜 / 镜时长必须完全一致，只改「人物」那一段提示词**，否则比不出谁唱得好，也剪不到一条时间线上。

### 选角与棚景海选：条件不统一就不要看

海选不是出几张好看的图，是**在统一条件下做横向比较**：

- **试镜卡四统一**：同一无缝背景、同一支 3200K 左侧 45° 柔光、同一件深灰圆领、同一 3/4 侧脸角度、都不笑。只有人不同，才比得出来
- 男女各 4 个，按**骨相／年龄／脸型**分型（圆短脸、长窄高颧、方脸宽下颅、瘦削深法纹各一个，年龄拉开），定 1 主 1 备。**不要用“沉静／冷感／文艺”这类气质词写提示词** —— 模型只能从骨相与胝部结构推脸，写气质就是八张一个模子
- 评图看三件：骨相撑不撑得住镜头、有没有磨皮塑料感、四个人能不能一眼分开。**光太平滑 = 塑料感，是重做的信号**
- 拼一条横向 contact sheet 再一次性问 vision（`ffmpeg -i a.jpg -i b.jpg … -filter_complex hstack=4`），不要逐张问
- 棚景出 3 个方向选 1（小型私人棚／老式模拟棚／明亮现代棚）。看三件：一眼能不能看出是录音棚、麦的位置清不清楚、光够不够拍脸（单灯顶光 = 死亡光，必须改成侧面柔光 + 暗部保留）

**AI 棚景的破绽全在设备上**：调音台推子排列乱、按键糊成一片、麦克风三脚架线条融化、时钟与排期表是乱码。**不要为这个重出图**，解法是“不让观众看清”：设备一律做浅景深虚化前景、时钟排期表用景别切掉；真要拍设备特写（比如推推子的花絮镜）单独出一张“微距虚化”图，别拿全景图裁。

### LibTV MCP 调用纪律（每条都白烧过一轮）

- `idempotencyKey` **只能纯 ASCII**（`^[A-Za-z0-9._:-]{8,255}$`）；写中文会只返回一段错误字符串、**没有 `task_id`**，看起来像“提交成功没反应”
- 对口型时 `startFrameNode` 与 `referenceAudioNodes` **不能同时传**（`Use frame roles or reference lists, not both`）：全走 reference 列表（`referenceImageNodes` + `referenceAudioNodes`）
- 音频进画布：`upload_ticket` → `curl -X PUT -H "Content-Type:"`（**必须去掉 Content-Type**，否则 OSS `SignatureDoesNotMatch`，python urllib 会默认塞 `application/x-www-form-urlencoded`）→ `upload_complete` → `upload_media` 挂节点
- **参数名不统一，报 `Field required` / `Extra inputs are not permitted` 先查名字，不要怀疑权限**：`upload_complete` 只收 `path` + **`upload_id`**（写 `uploadId` / 多传 `parts` 直接被 pydantic 拒）；`upload_media` 必带 **`projectId`**（漏了报 `PROJECT_REQUIRED`）+ `mediaType` + `fileRef` + `name` + `idempotencyKey`；`create_project` / `create_node` / `delete_node` / `generate_video` 全部必带 `idempotencyKey`。拿不准就用 `L.rpc("tools/list", {})["result"]["tools"]` 把目标工具的 `inputSchema` 拉下来看，比试错快
- 音频/视频 `upload_media` 首次几乎总是 `review_pending`（`nodeId: null`，`recovery.action: retry_same_operation`）：**用同一个 idempotencyKey 反复重调，直到返回里有 nodeId**（几十秒内）。不要换新 key（会挂出重复资源），也不要拿 `resource_info` 轮询——它只吃 `file_ref`、返回里没有 review 结果
- **节点显示名不能重**：同名再建报 `VIDEO_PREFLIGHT_FAILED: 已存在显示名为「X」的节点`。而 `run=false` 的只读预检**会在画布上留一个空壳节点**，真跑前必须 `delete_node`（带 key）清掉，否则同一个名字又被自己挡住。重跑同一镜一律给名字加后缀（`_720` / `_1080` / `_r1`）
- **`call()` 会把结果压成一句摘要**（`LibTV video: prepared.` / `... completed`），拿 task_id / nodeId / mp4 地址一律走 `L.rpc("tools/call", {...})` 自己解析 `result.content[0].text`；`read_project(view="nodes")` 里 `name` 常为 null，要名字或产物 url 就逐节点 `read_node`，再用 `re.findall(r'https://[^"\s]+\.mp4', text)` 取
- 授权链接**一次只发一条**：verifier 只存最后一次，用户点了旧链接那轮直接作废
- 批量建节点偶发「任务 SUCCEEDED 但节点没落进项目」：每批出完用 `read_project` 按名字逐个核对，缺的换个 key 重提（同 key 会重放旧结果）；也有反向情形——节点在列表里但 `read_node` 读不到 URL，那就在画布里看，不要重试
- 下载图不要只匹配一种 URL 特征：递归收集 `url` / `urls` / `originalUrl` 字段再按后缀过滤，比正则扫整段 JSON 稳

深度细节在 skill `libtv` 的 `14_演唱型对口型画布实测`（工艺卡、提示词骨架）与 `16_MCP接入与重新授权`（授权、账号等级、`COMMERCIAL_BLOCKED`）。

**群像默认会一起动嘴**：多人同框时必须在每一段写死“只有 A 张嘴，其余全部闭嘴”；做不到就只能拆单人镜交替或分屏。

**「先把风格定下来」= 写死六项，不是聊形容词：** 影调（机身/镜头/颗粒/暗角/调色）· 光（方向/色温/明暗分割）· 画幅与景别（脸占画面高多少）· 妆造（每件道具的材质）· 背景（什么环境、虚化到什么程度）· 字幕与包装（字体/位置/标题/文案）。六项定完全系列不改 —— 这是“固定电子人”的地基，改一次前面所有片子都废。

从用户发来的参考视频/截图反推这张卡、以及实测好用的“年代感 AI 演唱”风格参数，见 `references/演唱型风格卡与参考反推.md`。

### 场景图土不土，只差四件事（用户会直接说“很土、很俗”）

不要用功能词描述场景（「深夜便利店、冷白荧光、货架」——出来就是干净平淡的商品图）。每个场景提示词必带四件，**都不是形容词**：

1. **一个具体到反常的物**（还在冒热气的关东煮锅 + 靠在柜台的湿伞 + 地上一摊反光的水）—— 它是「人刚离开的证据」
2. **光有来源和状态**（过曝的自然光从开裂的天窗倾泻下来，而不是“冷白荧光”）
3. **空气里有介质**（蒸汽 / 尘埃 / 水汽 / 雨痕 / 薄雾）
4. **锁两种颜色并定占比**（冷青白 90% vs 暖琥珀 10%，只在关东煮那一块）

实测高赞画布的图片提示词中位只有 **170 字** —— 土不土不在长度，在上面四件。同一招也治「主题色没落地」：写「冰蓝」时必须把颜色写到发丝/丝巾/内搭/拼色包边这类**实物**上，只靠打光画面里几乎看不到。完整六段顺序、词频、反例、空镜与组合卡的分工，见 `references/演唱型风格卡与参考反推.md` 第六节。

### 长期运营：是一批人（常驻剧团），不是一人一条赛道

用户会说「就这么一群人、一个团队，一直拍这些歌，我给什么歌就有这几个主角去演」。这是**剧团模型**，不是四个 solo 歌手：

- **成员固定，曲风不锁人**：这周抒情、下周摇滚，同一个人都上；只要造型与声区不漂就不违和
- **每首歌做一次选角**：谁主唱、谁和声、谁客串、谁跑龙套（路人/听众/背景乐手）。一把嗓子唱得完就让其余人当配角；四个人都唱就全部是主角（轮唱/对唱/合唱）
- 人设按**可塑性**设计（性格反差是为了产生化学反应），不按曲风分赛道；观众记的是“这批人”，熟人感是这类系列唯一值钱的资产
- **形象必须清爽、干净、有个性。** 沧桑、邋遢、破旧是一次性情绪爆款的料（火完不能复用、接不了商单、做不成团队），长期厂牌一律不要往那个方向做
- 资产按「人 × 景 × 道具」建库并配成**组合卡**，一支歌 = 选角 + 1–3 个场景 + 1 个贯穿道具 + 六项风格常量不动

选角判据、场景按情绪功能分类、六条常量、资产库结构、群像拍法约束、场景提示词写法，见 `references/演唱型风格卡与参考反推.md` 第四、五、六节。

### 零成本路线：图文 / 素材轮播（真的不需要表演）

当一首歌**没有「人在唱」的表演需求、叙事靠物件与字幕**时，最优解不是「更便宜的演唱型」，而是**关掉整条对口型链**：歌手写真 + 图库素材 + 借鉴运镜轮播。没有嘴就没有口型可错，成本从「两天 + 付费重做」降到「半天 + 版税 0」。

**判据（两个都成立才走这条）**：① 歌词里有可拍的具象物（账本/化肥/缝纫机/登机牌）比人脸重要；② 用户接受「没有表演」，接受信息由画面质感 + 字幕节奏承载。反之，用户要「看到他唱」就是演唱型，见前面的第零道门。

| 素材类 | 占比 | 铁律 |
|---|---|---|
| 歌手写真 | 15–20% | 只放**副歌进入**与**结尾落点**；只能用背影/侧影/手/半张脸 —— 正面大特写会立刻暴露「她没在唱」 |
| 图库素材 | 60–70% | 必须**逐张识图建语义目录**（按组：老屋/账本/麦田/缝纫机/昏灯/归乡/手），再按歌词锚点取图；禁止按文件名或空档塞 |
| 借鉴运镜 | 15–20% | 同一批素材做 Ken Burns（1.0→1.08）+ 4–8 帧叠化；副歌处可叠二重曝光（账簿 × 麦田）做「记忆叠印」 |

**切换频率由能量曲线决定，不凭听感：** 先把歌量一遍（BPM、调性、每 2 秒 RMS 归一化到 0–100），能量 20–40 的段 **8–10 秒一格**，副歌 70–100 的段 **2–3 秒一格**，结尾最空的那段只给 1–2 张不切。段落表本身就是剪辑节奏表；峰值处给最强的一张画面，谷值处必须给最空的一张。

```bash
# 量能量（能跑 librosa 的 venv）
env -u PYTHONPATH -u VIRTUAL_ENV -u PYTHONHOME /opt/lipsync-venv/bin/python - <<'PY'
import numpy as np, librosa
y,sr = librosa.load("song.mp3", sr=22050, mono=True)
bpm = float(np.atleast_1d(librosa.beat.beat_track(y=y,sr=sr)[0])[0])
ch = librosa.feature.chroma_cqt(y=y,sr=sr).mean(axis=1); k=int(np.argmax(ch))
hop=sr*2; rms=np.array([np.sqrt(np.mean(y[i:i+hop]**2)) for i in range(0,len(y)-hop,hop)])
print(round(len(y)/sr,1),"s BPM",round(bpm,1),"RMS",(rms/rms.max()*100).round(0).astype(int).tolist())
PY
```

**三条风险与对策（都会真发生）**

1. **素材撞车**：公开图库同期可能被别的账号用过同一段 —— 每格做二次构图（裁切/水平翻转/调色），不原样钺
2. **图库偏外国感**：欧美乡村的老屋/麦田跟中国九十年代农村有距离 —— 优先选**无地标特写**（手、纸、缝纫机、包装袋），少用带建筑风格的全景
3. **像 PPT**：靠切换频率 + 叠化 + 二重曝光破，不要兼用「每张都推一下就完事」

素材站可用性、可直接抓的 URL 规律、授权红线，见 `references/素材站与图库轮播.md`。

**每开一集先填 `templates/导演计划.md`**（歌 → 主角远近法 + 三识别符 → 场景地图 → 素材来源矩阵 → 工时 → 执行清单）。没这份就不开工：没有场景地图，必然在“素材不够 / 关键词货不对板”上返工。

**单素材全片 ≤4 次**：分镜落盘后先看 `Counter(src)` 的 top1，超了就把池子调大或退到全量池——否则 200 秒里同一个画面会出现十几次，用户一眼就是“画面重复”。

## 第一道门：蹭爆款的红线

用户说「蹭一下热度，出个同版」时，先分清能蹭什么，再动手：

| 做法 | 判定 |
|---|---|
| 蹭形式、体裁、赛道（同样是「古人说唱」、同样是 AI 漫画 MV） | 可以 —— 创意与体裁不受著作权保护 |
| 换阵容、换主题、词曲全原创 | 可以 |
| 抄对方的歌词、旋律、编曲 | 侵权 |
| 抄对方的具体角色设定与台词 | 侵权 |
| 标题写「《某某》同款」「某某复刻」 | 高危 —— 平台判仿制／搬运，直接限流 |

默认走**同赛道第二集**：形式照搬、内容全换。然后主动提醒用户投放文案里不要出现原作品名 —— 这一步用户自己最容易忘。

### 「大致雷同」和「洗稿」的分界

用户说「只可大致雷同，切不可抄袭」时，他要的是：**形式骨架可以像，字句不能像**。三种最常见的越线，都发生在「看起来已经改过」的情况下：

| 越线方式 | 例 | 为什么算抄 |
|---|---|---|
| **同义词替换式洗稿** | 原作「你熬的夜 你咽的话 你没赢的仗 我都有份」→ 改成「你加的班 你背的锅 你没保住的人 我也有过」 | 三段排比 + 同位置收「我也有」，结构完全照搬，只换词 |
| **开头几字重合** | 原作「我不是来教你的」→ 改成「我不是来教你怎么赢」 | 开头五字相同，读者一眼认出 |
| **段落骨架一致** | 原作「我是某某 + 你也一样吧 + 三人合唱」十段循环 → 改成五段同位置循环 | 骨架是受保护的表达，不是「通用手法」 |

**自检三条：** 连续 8 字以上有无重合；排比／对仗的**结构**是否同形；钩子与收尾的**位置**是否一致。中任何一条就重写整段，**不要只换词**。

**可以借的只有：** 体裁（古人说唱）、场景母题（围麦克风／开放麦）、叙事逻辑（至暗时刻 + 当代对照）、以及「你也一样吧」这类**极短通用口语**。

## 爆款形式拆解：先研究原作怎么赢，再动手

用户说「蹭这个爆款」时，第一件事不是出图，是把原作拆到能复述的程度。**拆完往往发现成功要素和直觉相反。**

以「古人开麦说唱」这类破亿播放的片子为例：

| 维度 | 实际做法 | 反直觉点 |
|---|---|---|
| 音乐 | 平平淡淡地唱，没有炫技 flow、没有炸裂 beat | **不是快、不是燃** |
| 人声 | 保留自然的停顿与叹息感 | 卡拍精确反而毁掉它 |
| 场景 | 单一小酒馆、昏黄灯光、围站麦克风 | 场景越简单越好，成本几乎为零 |
| 结构 | 三段主歌（各代表一种人生境遇）+ 群像推进 + 副歌 | 不是 N 个人平均分配 |
| 每段钩子 | 一句固定口语，同位置重复 | 重复才成记忆点 |
| 每段收尾 | 多人合唱同一句 | 集体声盖过独唱，情绪抬起来 |
| 内容 | 只讲至暗时刻，不讲功业 | **伤疤才共鸣，成就不会** |
| 立场 | 不说教、不给答案，「我也经历过」 | 鸡汤式结论立刻掉粉 |

**从这张表里能直接拿走的四条铁律：**

1. **直插主题，0 秒就给最狠的。** 开场不要铺垫场景、不要年代字幕、不要氛围镜头。第一个字就是伤疤。（原作第一句是「我是杜甫，一辈子都在搬家」。）
2. **每位主角用「倒叙 + 首尾回扣」：** 第一句甩出最狠的结果 → 倒叙怎么走到这一步 → 最后把同一句再砸一遍。首尾咬合的这句是全段力量所在。
3. **平淡比炫技难做，但平淡才传得开。** 语速 3 字/秒左右，关键句后留 1.2–1.8 秒气口（叹息感）。为了「有节奏感」去卡拍、提速、加压缩，会把叹息感磨掉 —— 那是这类片子唯一值钱的东西。
4. **具体物件代替道理。** 不写「我很孤独」，写「车里装满了咸鱼」「树上那根绳子是我自己带的」。一个镜头能讲清的句子才有用。

**做完拆解再动手，不要边做边猜。** 方向错的时候，越用力离得越远。

**拆解要量、不要只看**：搜索 → 取元数据（播放/赞/时长）→ 下 480p 样片 → `ffmpeg` 数剪辑点算均镜长 → 抽 4 帧拼图逐帧判读。均镜长 + 有没有人真唱，是唯一能把「形态」说清楚的客观量。完整命令、风控绕行与判读口径见 `references/对标MV形态实测.md`。

### 爆款是系列跑出来的，不是单条命中的

拆原作时顺手看一眼它的**发布史**，这决定你该怎么跟用户谈预期。

实测那条破亿的片子是同一账号「古人开麦」系列的第 **8** 期 —— 系列一个月前就开始发，前 7 期是历史人物说唱对战，到第 8 期才改成多人合唱并爆掉。创作者本身是电视台导演转个人工作室、被平台认证的 AIGC 作者，不是素人灵光一现。

**对用户的话术：** 首条没爆是常态，不是失败。正确做法是把「同赛道」当系列做 —— 一次设计 3–5 期选题（换主角阵容、换处境角度），第一条验证形式，后面靠调整迭代。不要把全部预算压在单条上，也不要用「首条必须爆」给自己设死线。

## 第一点五道门：情绪定调来自原始 brief，不要自己发明

给**别人（或别的 bot）生成的歌**做 MV 时，第一件事是索取或复述这首歌的**原始创作 brief**：编曲核心、人声质感、起手设计。

MV 的情绪曲线必须与**编曲曲线**一致，不能凭自己听感或流行套路定调。实测教训：只因为“歌是欢快快嘴”就把基调定成“反差喜剧（爽的惨）”，被 brief 直接纠正 —— 真实意图是**「从憋到炸的宣泄」**：主歌压着、副歌合成器与重低音突然铺满、多层人声大合唱、把副歌做成“打工人精神信条”。“反差喜剧”只保留了“憋”的一半，漏掉“炸”和“集体”，拍出来就是一部情绪对不上的片子。

四条硬规则：

1. **brief 里的起手设计就是第一镜。** 写“第 0.5 秒干声 Punchline 砸脸、紧接着低音全开”，画面就必须是黑屏或极近特写 + 一记震动（机位下压/整帧抖），**不能是仰拍大楼这种渐入**。
2. **brief 写了“合唱/齐吼”，画面必须有群人。** 从**第一次副歌**起就要有集体感（主角 + 身后一排排人同时张嘴、天花板被掀开），不是只有主角一个人挥拳。三次副歌靠**规模**递增（一排 → 整层 → 整栋），不是靠同一动作加重。
3. **主歌按实测字速切。** 5.75 字/秒 ≈ 每 2 秒一句 → 一句一格，画面 2 秒一换；不要一个镜头里让他跑半天。
4. **多阶段渐变不要平摊全片。** 先看歌词时间轴：若“周一到周五”这类渐变只集中在 Bridge 的 8 秒（每天 2 秒），就把细节全砸在那 8 秒（**同机位、同构图，只换状态**），其余时段讲透一件事。平摊到全片的结果是每天都没拍透。

**用“一个可见的物理量”承载情绪。** 体格／电量／咖啡液面这类可测量对象，比“表情要疲惫”更省、更稳、AI 更不容易崩，而且观众三秒就懂；首尾用它做闭环（满杯 → 见底 → 又一杯），不用一句旁白。

### 顺序固定：编导 → 审核框架 → 风格图 → 选人

用户会直接纠正这个顺序（“你现在思路是混的”：还没定编导就去出风格图）。正确顺序四步，不许跳：

1. **读歌的气场**：从曲风/BPM/调性/人声音域/编制/歌词母题反推“这首歌在讲什么、是什么姿态”（是哭、是求、还是迟到多年的一次开口），一句话说清
2. **出编导案**：谁在唱、在什么地方唱、为什么在那里唱、情绪曲线分几段、贯穿道具是什么
3. **先立审核框架**（拍前定，不是拍完再说）：气场对不对 / 场景成不成立 / 情绪有没台阶 / 口型真对上没 / 包装超没超标——每条给可判定标准与不过怎么办
4. **才动风格图与主视觉**，最后选人（先做一个试）

**编导案里必须有“三个必须”级别的硬动作**（如贯穿旧物出现≥3 次、桥段必须抬头看远处、结尾必须回到日常空间不给和解），否则拍出来只有情绪没有戏。

## 第二道门：先出音频，点头再配画面

用户听到歌之前，不要动画面。出歌 → **只发音频** → 等一句「可以」→ 才做分镜。

理由：歌是唯一会让整条时间轴作废的东西。改歌词、剪前奏、换混音，任何一项都会让已出的分镜图和排好的镜头时长全部重来。一次性做到成品看着省事，方向一错浪费的是整个后半程。用户会明确要求「先让我听一遍歌，行不行」——照做，不要连做到底。

**但这条只管「停在哪个节点」，不管「节点内部要不要问」。** 节点一旦定下，就一路做到下一个可判断的交付物，中间不要反复请示。实测出现过：方案已确认、用户已说「搞」，仍然回头问「要我直接开始吗」——得到的是「你直接开始啊，不用问我」。**方案阶段要讨论，执行阶段不要问；需要用户判断的只有交付物本身。**

## 第二点五道门：写镜头的提示词要按规格书，不要按散文

分镜表定完、开写每镜提示词之前，**先加载 `references/镜头提示词规格.md` 并按它走**。

三个必须有的前置物：

1. **全局锚点表**（主体/场景/光效/声效四个锚点）—— 定了才有统一约束，每个镜头的提示词都要把它贴进去
2. **CONTINUITY RULE 的屏幕方向** —— 双人对峙戏写死「谁在画面左侧、谁在右侧」，这是越轴的唯一解药
3. **LIGHTING 稳定性要求** —— 一句话「基础光效不因剧情紧张程度改变」，全片才不会每镜飘光

**自查方法**：镜头表写完后挑两镜并排看，如果除动作描述外没有任何一句是重复的（锚点串／光效／方向），说明没有统一约束，全片一定会飘。

空间上另有五条硬约束（轴线同侧 180° 半区、中景以上禁侧面 90° 正拍、禁同景别硬接、禁特写与全景直切、多人同框要同一基准线与焦距），全部在 reference 里。

## 第三道门：不要为局部缺陷换整体方案

这是本类任务最贵的教训，单独成节：

**用户认可的那个版本，它最大的优点就是不能碰的东西。**

「咬字糊」是最常见的返工诱因。正确解法按代价从低到高：

| 缺陷 | 最简解 | 不要做 |
|---|---|---|
| 咬字糊、字听不清 | **加字幕**（观众靠眼睛） | 换演唱引擎重做整首歌 |
| 前奏太长 | 剪掉前奏，重排时间轴 | — |
| 人声干、刺、塑料感 | 后期链：高通 → 减浑浊 → 提清晰 → 去齿音 → 压缩 → 混响 | 换模型 |
| 音高平、像念经 | 在**原有引擎内**改音高设计 | 换模型 |

**为什么换引擎是灾难：** 整曲生成模型（ACE-Step 这类）的强项是唱腔、情绪、呼吸感 —— 它是在「唱」。逐字拼装的 SVS（SoulX-Singer 这类）字准，但天然没有人味 —— 机器在「念」。为了 10% 的咬字准确率换掉它，等于把 90% 的音乐性一起丢掉，听感会变成「跟鬼捏到喉咙一样」。

**判据：** 换引擎会让整首歌的听感全部重做，所以它只能是最后手段。动手前先问一句「用户认可的那个版本，好在哪」——那个点一个字都不能动。

## 第四道门：交付前自己用观众的耳朵过一遍

技术指标全绿不等于成品能用。`ffprobe` 时长对、文件能播、字数没错，都不代表好听。

每次出片前自己完整听一遍／看一遍，用普通观众的判断，不看参数。用户的第一句反馈常常是「你自己听过没有」——这条规矩就是这么来的。

## 第四点五道门：把方案 + 真实数据交给外部模型审查

方案写到自己觉得完整之后，**把它连同真实的市场数据和实测指标一起发给一个强模型，只问「哪里会死」，不问「好不好」**。这一步的产出往往不是加法而是减法。

提问要包含三样，否则会得到一堆正确的废话：

1. **完整方案正文**（SOP、歌词、分镜思路全贴，不要摘要）
2. **真实数据**：同赛道播放量排行、自己已实测的成品指标（F0／时长／咬字率／节拍）
3. **明确的输出格式**：「致命问题 / 重要问题 / 必须补的步骤 / 一句话结论」

### 审查的价值在砍东西

实测把 6 处「升级」交给外部审查后，被砍掉一处（每镜都加运镜），另有两处被改成低成本版（N 套完整布景 → 公共舞台 + N 张背景；40 镜对口型 → 12–16 镜关键近景）。

**自己提的升级里，至少有一处是堆料。** 典型特征是「每个都要做」—— 每镜都动、每一句都对口型、每个人物都换装。看到这种均质化的「全面升级」就先怀疑它。

审查会给出一个**优先级链**（例：接话成立 > 关键口型可信 > 低成本换景 > 全镜运动）。拿到后按这个链排施工顺序，不要按自己原来的顺序做。

### 调用时的两个工程坑

- **长 prompt 会断连**：单次 5000+ 字符 + 大 max_tokens 常报 SSL 断连或 `Remote end closed`。拆成多轮、每轮 1200 字内、max_tokens 2500 左右，成功率高得多。用 Python `urllib` 发大 body 也容易断，**用 curl + 写到临时 json 文件 + `-d @file`**。
- **一次只问一个维度**：把七个问题塞进一次请求，大概率超时且回答笼统；拆成 2–3 轮反而快。

### 反过来用：让它从「它听不到的歌」推导画风

外部文本模型听不了音频，但能读图。把歌编码成它能吃的三样，它给的画风方案质量足够直接开工：

1. **歌词时间轴**（自己排的 LRC/SRT，标到 mm:ss）
2. **实测节奏数据**：BPM、拍间隔标准差（是否量化鼓机）、16 分格鼓型、逐句字速、能量走向、频段明暗
3. **整曲 mel 频谱图 + RMS 曲线**，图上用虚线标好段落切分 —— 这是它的「耳朵」

实测价值：它会拿节奏数据去定剪辑点（主动引用了「底鼓重音落在 16 分格第 5 格和第 15 格」），并用明暗数据否掉不合风格的选项（频谱偏亮 → 否决暗色霓虹/lo-fi）。**给频谱图 + 实测数字，比给它一堆风格形容词有用得多。**

要它按固定结构输出，否则会写成散文：①一句话画风 + 3 个候选及适配理由 ②定版规格（色彩/光线/镜头语言/质感/角色造型/字幕留白） ③N 镜分镜表（时间区间 / 画面 / 运镜 / ≤25 词英文出图 prompt） ④黑名单 5 条 ⑤「只能改一处改哪里」。硬约束单列一节并写明不要建议突破（竖屏 9:16、成片时长、必须能被 AI 图/视频模型生成、不要真人实拍）。

## 第四点八道门：提示词 SOP 要先调研再定稿

用户会明确要求「不要闭门造车，一定要去调研」。视频模型的版本迭代很快（单次时长、关键帧数、参考素材上限都在变），**拿旧模板直接开写就是错的做法**。定稿前至少查两件事：当期模型的能力上限（单次可多长、能不能多关键帧、参考素材几项）与行业正在用的提示词框架（四层结构、光影写法、运镜词表）。

调研结论要**回灌到 SOP**，不是只汇报 —— 实测一轮调研直接改掉了三处做法：长镜头可以直接做 10–15 秒不必切碎、全片只收一个光源、角色一致性改用「角度集合图 + 每镜首句锁参考」。

## 第五道门：批量之前，每一环先烧一个单镜

后面几个环节（图生视频、对口型）都是按「镜」计费、按小时计工时的。**批量做完才发现不对，是本类任务最贵的一种失败。** 三个单镜门，每个只花 10 分钟：

| 门 | 做什么 | 不过怎么办 |
|---|---|---|
| **时长门**（出图前） | 把分段音频拼成全曲，`ffprobe` 实测总长 | 偏离目标 >15% 就回去补/删歌词重生成；**不要拿估算值排分镜** |
| **图生视频门** | 挑最激烈的一段出 1 条 5 秒视频 | 比对静态图，脸／服装／光飘了就换首帧图重做（不回退角色图），最多试 3 张 |
| **对口型门** | 拿这条 5 秒视频 + 对应那句人声做 1 次 lip-sync | 见下方三级降级 |

### 画风定稿后的第一批单镜是「验可生成性」，不是验画风好看

方案定稿后先按**最难的 1–3 镜**各烧一张，判的不是美不美，而是这个概念**静态图能不能表达**：

| 概念类型 | 静态图 | 处理 |
|---|---|---|
| 光影、剪影、透视延伸、半透明分身、超现实并置 | ✅ 一次就出 | 直接进分镜表 |
| 物理变形、物体折叠、连续位移（「桌面沿中轴折成一条路」） | ❌ 只给「透视上的路」，不给「物体折开」 | 交给视频模型（首帧→尾帧）或拆成 15°/45°/75° 关键帧做动画 |
| 画内可读文字、日历、招牌、屏幕字样 | ❌ 必糊 | 改写成不靠文字表意 |

**首帧和提示词打架时，改提示词去描述首帧实际画的东西，不要指望视频模型把两者缝起来。** 上游出图模型会把「物理变形」这类梗静默降级成它肯画的东西（想「把身体压成纸片贴玻璃」→ 出图是「他的海报贴在玻璃上」）。降级后的画面往往照样成立（意象还在），但前提是图生视频提示词按**图**重写而不是照抄原稿；照抄原梗 = 提示词与首帧对立，两头不到岸。顺序固定：逐张比对 → 按图改词 → 图完全不可用才重出。三种典型降级形态与处理见 skill `kling-prompt-quality-gate` 图生视频第 4 条。

同一次核对里还要查**跨镜头是不是同一张脸**：提示词只写服装颜色（如 `coral blazer`）时，实测两张就出现黑发/金发两个人。角色按「跨镜头人物一致性」那节写死发色发型脸型，或先定一张角色设定照再逐镜锁。

### 报进度时先把「片长」和「耗时」分清

按镜批量生产会跑几小时，**不说清楚，对方会以为你要交一部几十分钟的片子**。每次报进度把三行摆出来：

- 成片长度 = 歌长（如 5:10）
- 每镜长度 = 5 或 10 秒（单镜接口上限）
- 生成耗时 = 镜数 × 单镜耗时（**因为是 N 次 API 调用，不是视频长**）

**并发能力要主动提，不要等对方问「这么久吗」。** 同一个账号的并发额度能把串行几小时压到几十分钟，报耗时的时候一并给出两条选项让对方选。

**进度报的应该是内容维度**（哪一段/哪一句的镜头完成了），不是只报 `xx/66`。数字进度对用户没有意义，他要知道的是「现在做到哪一句了」。

### 核对必须是内容核对，不是只查技术指标

「图没崩、分辨率对、时长对」只证明素材能用，**没证明它属于这一句歌词**。每次核对把这一镜的歌词摆在旁边问：

- 这个画面的情绪和这句词对得上吗？
- 人物的动作/眼神在说这句词，还是只在镜头前站着？
- 把人声静音，光看画面能猜到是哪一段吗？

技术指标会放过一批「很干净但完全不对位」的素材；内容核对才会把它们抓出来。

**时间基准全局只能有一个：全曲拼接后的那个文件。** 分镜、字幕、口型对齐全拿它算。分段音频和全曲各算一套，最后必然对不上 —— 而这种错会一直潜伏到第 ⑦ 步才爆，前面出的图和视频全废。

### 对口型对不上时的三级降级

快速咬字（说唱、密集短句）对口型是整条链最大的不确定点，**不要假设它能过**：

1. **只对关键句** —— 每段段首最狠那句 + 段尾回扣那句，其余用侧脸／背影／低头／道具特写掩盖
2. **全改氛围镜** —— 放弃口型，人物闭眼／仰头／手部动作，内容交给字幕承载
3. **换工具** —— 其它 lip-sync 方案或本地 SVS，需重新验证

**装配完再降级的机会成本极高**（视频已全部生成），所以这道门必须在批量前过。

### 咬字验收要量化到字，不能凭感觉

用 `difflib.SequenceMatcher(None, 原文去标点, whisper 文本).ratio()` 逐字算：

- 整体 **>70%** 合格
- **每段最后几句（要砸的那几句 / 副歌）要求接近 100%** —— 这几句错了，字幕一直在眼前晃，观众一定会发现
- 低于 70% 时先回炉改词（见 `minimax-music3-local` 的声母混淆天花板），而不是先怪录音

## 流程总览

```
歌词 → 出歌（见 local-music-generation）→ whisper 拿时间轴
     → ComfyUI 出漫画分镜 → vision_analyze 批量验图
     → ffmpeg 逐段运镜 → ASS 字幕 → concat + 混音频
```

一条 2 分钟的竖屏 MV 全流程约 20 分钟：分镜单张 2.5–5 秒，约 20 张一分钟内出完（张数由唱词决定，见「一点五」），瓶颈在出歌和编码。

### 3 分钟以上的长片必须分段

单次整曲生成有硬上限（ACE-Step 实测约 130 秒）。做 5 分钟这类长片时，**按段落各自独立生成再拼接**，不要一次生成长曲再切：

- 每段 55–90 秒，完全在模型能力内，质量最稳
- 每段可配不同 BPM／调性／主奏乐器 —— 多主角的片子靠**编曲差异**区分角色，不靠音色（省掉最难做的多音色克隆）
- 某段不满意单独重做，不连累全曲
- 接缝做成设计感：段尾「编钟／鼓单击 + 半拍静默」，拼起来听不出断层

生成细节见 `local-music-generation`。

配图有三条路线（可灵图生视频 / 本机固定卡通人物 / 静帧运镜），成本与适用场景差别很大，**先按预算和用途选路再动手** —— 见 `references/配图路线选择.md`；可灵那条路的完整执行逻辑（鉴权、批量提交、计费、余额查询、长镜补足，以及 `cfg_scale` / 动作式提示词两个「动不动」开关）见 `references/可灵批量图生视频.md`。

## 镜头按四类分，不要全片一个成本

预算是按镜算的，而**不是每一镜都值得花钱让它动**。先把分镜表按四类切开，再决定哪类上付费模型：

| 类 | 功能 | 单镜时长 | 用什么出 | 理由 |
|---|---|---|---|---|
| **① 转场** | 场景切换、时间推移 | 1.5–2.5s | 静帧推拉 | 空镜，**再真的运动也看不出来** |
| **② 花絮** | 道具/局部特写，剪辑调料 | 0.9–1.2s | 静帧推拉 | 一个推近就够，一秒镜头不值3元 |
| **③ 对唱对怼** | 两人同框对峙 | 3.5–6s | **付费图生视频** | 两个人都在动，静态图一眼假 |
| **④ 正脸怼拍** | 怼脸开唱 | 5–8s | **付费图生视频** | 全片主体，必须有身体语言 |

**判断口径只有一个：这一镜里观众的眼睛在看什么。** 看脸和嘴 → 必须动（③④）；看环境和氛围 → 推拉够了（①②）。

实测配比：48 镜的片子里，③④ 只占 22 镜（约 53% 时长），全量上可灵要 145 元，**只把 ③④ 上可灵降到 66 元**，而降下去的那 26 镜全是一两秒的空镜和特写 —— 观众根本分辨不出。

**反向的坑：把 ② 花絮镜也上付费模型。** 花絮镜头本来就只取 1 秒，模型出的 5 秒里 4 秒被丢掉，纯浪费。

**「动画」这个词必须先问清，它其实有三层。** 用户说「配动画」「动画 MV」时，经常指的并不是你以为的那一层：

| 层 | 做法 | 观众看到 | 成本 |
|---|---|---|---|
| ① 静帧推拉 | ffmpeg zoompan | 照片在缓慢放大 | ¥0 |
| ② 唇同步 | Sonic / lip-sync 接口驱动嘴型 | 嘴在动，**但人不动、背景不动** | 本地免费或云端付费 |
| ③ 图生视频 | 可灵 omni-video 这类 | 身体、手、头、背景都在自然生长 | ¥3/镜起 |

**② 经常被误交付成 ③。** 唇同步模型的本质是「把一张静态图的嘴部按音频变形」，背景、身体、衣服全部静止 —— 用户一句「你一张图传进去，其他东西都不动，纯粹去对口型而已」点破的就是这个。交付前自己判断：这个镜头的画面，除了嘴，**还有别的地方在动吗**？没有就是第②层，必须主动说清，不要含糊成「动画」。

第②层不是没用 —— 它能做到「嘴型精确到字」，第③层做不到。**正确的用法是把它定位成「特写镜」：人物大特写、只需要看清嘴型时用它；其余镜头用③。** 两者混剪比全片都用②好得多。

**用户要「饱满」时不要省。** 明确说过不要小气／要丰富时：镜头数翻倍（每位主角 9–10 镜而不是 4 镜）、用可灵 pro 1080p 而不是 std 720p、预留 30% 重做额度。默认省钱的方案在这个语境下是错的。

**反方向同样成立：一出现「多少钱 / 1080p 慎重 / 太贵了」就立刻停手并算账。** 做法：立刻 kill 还在跑的高规格任务（后台队列会持续烧钱）→ 先报 `条数 × 秒数`，并分开「已花掉的沉没成本」与「还没花的部分」（已出的重做只是再花一遍）→ 给最省/推荐/保画质三档让他一句话拍。

**成片默认 720×1280。** 竖屏交付规格历来就是 720p，拖音够用；而且若一半镜 1080p、一半 720p，`xfade` 会直接报错退出（尺寸不一致）——要么全统一，要么拼装前每段先 `scale+pad` 到同尺寸（实测这是“拼接莫名其妙失败”的常见真因）。

**花絮/插图插入镜一律不上 AI 视频。** 静帧 `zoompan` 极缓推拉（推进/拉远/横移交替，别十条一个方向）零成本且比生成更清楚；只有需要视差、光变、尘埃、物体运动时才值得付费。一条 5 秒花絮里能看到的只是 1.5–3.5 秒，付费生成的那几秒大半要丢掉。

## 一、先拿到时间轴，不要靠猜

镜头切换必须卡在唱词上。**时间轴优先用素材自带的 SRT／LRC（作者给的才是真相源）；没有现成字幕时才用 whisper 转写 —— whisper 对「唱」字错且时间粒度只有 3–5 秒，见下方「拿到作者原始 SRT」一节。**

```bash
curl -s -X POST http://127.0.0.1:8890/inference \
  -F file=@"song.mp3" -F language=zh -F response_format=verbose_json
```

端点只接受 **`/inference`**；`/v1/audio/transcriptions` 返回 `404 File Not Found`。

返回的 `segments[]` 每段有 `start` / `end` / `text`。**字幕文本用原词，不要用 whisper 转写的字** —— whisper 对带 BGM 的唱段会错字，而字幕必须是正确的；时间轴用它、文字用你自己的。

### ⚠️ 拿到作者原始 SRT 时，不要用 whisper 复核时间

**whisper 在「唱」上的时间戳同样不可靠，不只是字错。** 实测对一条 166 秒的说唱干声（`04_纯人声` 单轨、无人声混响干扰）跑 `verbose_json`：

- 时间戳粒度只有 **3–5 秒**（`0.00-5.00` / `5.00-8.00` / `8.00-12.00`），做不出逐句卡点
- 字全错，而且错得很随机：`皇帝的排场`→`皇帝的牌唱`、`三百万的岗亭`→`三百萬的鋼琴`、`见我要签字就拦`→`見我要簽字就攔截了`
- **纯器乐尾奏会幻觉出重复句**：末尾四段全吐同一句，白白多出 12 秒

**判据：** 素材带官方/作者给的 SRT 或 LRC 时，那就是时间轴真相源，直接用；whisper 只用于「没有现成字幕的原创曲」。并且先自己抽 3 个时间点看字幕落点对不对，再去怀疑字幕参数 —— 多数「字幕做得不行」的投诉，**时间轴是对的，错的是字号／描边／MarginV**。

同时看一眼 `segments[0].end`：整曲生成模型常给一段很长的纯器乐前奏（实测 130 秒的歌前 26 秒无唱）。超过 10 秒就说明短视频版必须剪掉前奏，或者字幕上得提前把这段填满。

### 先过滤 ad-lib，再排镜

`segments[]` 里会混大量模型自加的填充词：`yeah~` `hey~` `欸~` `喔~啊~`。这些不是唱词，照坐进分镜会得到一堆没意义的镜头和乱码字幕。先过一道：

```python
import re
def is_adlib(t):
    t = t.strip()
    return bool(re.fullmatch(r'[a-zA-Z~\s]{0,12}', t)) or t in ('耶~', '欸~', '喔~')
real = [s for s in segs if not is_adlib(s['text'])]
```

实测 98 段里就有 13 段是 ad-lib（占 13%）。

### ⚠️ 出图前必须先过「重复段」这道门（否则白烧 20% 的图）

**整曲生成模型在歌词唱完后不会停，而是把已有段落再唱一遍。** 如果直接按时间轴出图，那部分时长会拿到没有新内容的镜头 —— 钱花了，成片却在水。

实测一条 224 秒的片子，重复段合计 50 秒 = **22%**：

| 位置 | 重复内容 | 白占 |
|---|---|---|
| 35–47s | 同一句唱 3 次 + 尾句再 3 次 | 12s |
| 96–112s | 整段 Verse 重唱 | 16s |
| 200–222s | 尾句唱 4 次 | 22s |

**检测方法（拿到时间轴后立刻跑）：** 把 `real` 的 text 归一化（去标点、去空格）后找重复串；再看相邻段的文本相似度。任一重复块超过 8 秒就是水。

**处理顺序：**
1. **首选回炉改歌词**：每段写到 12–14 句（实测 8 句必循环）。词够长，AR 就不循环，时间轴自然干净，不用剪
2. 已交付音频不能动时，剪掉重复段重排时间轴（注意歌词与字幕同步）
3. **不要先出图再发现重复** —— 这是本类任务成本最高的返工

### 咬字体检：whisper 对不上原词 = 口型路走不通

把 whisper 的转写和你自己的原词对一遍。如果大面积对不上（实测出现过「我把六家打成一摊」→「我把六甲打成一堂」、「树上那根绳子」→「树上那根松子」）：

- **走字幕路线**：无影响，字幕用你的原词
- **走对口型路线**：口型会对不上字，必须先把咬字改好再上 —— 改法是换词不是换引擎，见 `minimax-music3-local` / `diffrhythm-song-generation` 的错字黑名单

### 句子时长分布：决定镜头张数

实测句均 2.33 秒（最短 0.84 / 最长 4.56）。**一句一镜会让一半镜头不足 2 秒，切太快。** 按**每 5 秒一个画面**重排更稳：

```python
for i in range(0, total_sec, 5):
    cur = [s for s in real if s['start'] <= i < s['end']]
    print(i, cur[0]['text'][:20] if cur else "（间奏/静音）")
```

输出里出现连续的「（间奏/静音）」就是间奏，给它空镜（宫灯／雨／烛），不要留黑。

## 一点五、设计动线：镜头数从唱词长出来，不要先定张数

用户说「把动线设计得漂亮」时，要的不是「多配几张图」，而是镜头之间的推进逻辑。做法：

**镜头数 = 实际演唱句数 + 前奏镜头 + 尾奏镜头**，不先拍一个数字（如「17 张」）再往里塞。一句唱词一个镜头，镜头时长直接取 `segments[]` 的 `start`/`end`。最长的那句（通常是 Chorus）自动得到最长的镜头。

**三条推进线同时走**，片子才有「动」感：

| 线 | 例 |
|---|---|
| 空间 | 高处俯拍 → 半高（天桥）→ 低处（车厢、街边）→ 回到高处 |
| 时间 | 深夜 → 凌晨 → 天亮 |
| 情绪 | 旁观 → 具体困境 → 集体共鸣 → 短暂温暖 → 无人解答 |

**运镜四种轮换，不连用同一种**：推（进入内心）/ 拉（抽离）/ 横移（旁观）/ 固定（凝视）。全片都推会像 PPT，全片固定就是幻灯片。横移用 `zoompan` 的 x/y 偏移实现（`z=1.12` 固定 + `x` 随 `on` 线性走），垂直摇用 y 偏移，不要只会 zoom。

**情绪靠物件承载，不靠嘴**：手、酒杯、书页、红笔、头顶 —— 特写只给物件。这条与「不对口型」是同一个决定的两面。

## 二、出漫画分镜（ComfyUI flux3）

### 先定一件事：要不要对口型

有两条路，**先问用户要哪种**：

| 路线 | 做法 | 适用 |
|---|---|---|
| **不对口型**（默认） | 主角全程不张嘴；分镜只用背影、侧脸、低头、手部特写、远景；负面词写 `open mouth, teeth showing` | 静帧运镜、快节奏、多人物群像 |
| **真对口型** | 静态人物图 → 可灵 `omni-video` 出 5 秒微动 → `/v1/videos/lip-sync` 用音频驱动口型 | 人物站在麦克风前说话／唱（「古人开麦」这类） |

**以前写的「卡通人物 + 中文说唱对口型必崩」是错的。** 那句话是「只用图生视频提示词硬凑口型」的结论；走 `lip-sync` 接口实测口型开合自然、有说话感、脸不崩、画风守得住。参数与切片方法见 `references/可灵批量图生视频.md` 第八节。

对口型的成本约束：**不要全程口型**（每 5 秒一个片段会变成 60+ 片段、400 单位）。每位主角 2 个口型镜头（段首最狠那句 + 段尾回扣那句）就够撑住「他在唱」的感觉，其余用静态图运镜填。

### 跨镜头人物一致性：详细角色描述串就够，不用 Edit 修

先按「一角色一串」写死外观，具体到发缝、鬓角、黑眼圈、衣服颜色、身体比例，每张图都贴同一串：

```
a tired 45-year-old Chinese man with grey hair at both temples, short messy black hair,
heavy dark circles under small tired eyes, drooping eyelids, round face, stubble,
wearing a dark charcoal grey short-sleeve t-shirt and dark trousers
```

实测 8 张（正面/侧脸/全身/后背/4 个表情）是同一人。**不需要 Qwen-Image-Edit 修脸**——省掉一整圈工作量。

### 画风选型：跨场景一致性优先，不用最好看的那个

| 画风 | 跨场景稳定性 | 结论 |
|---|---|---|
| **美式粗线平涂** | 最高 | ⭐ MV 首选 |
| 日漫扁平 | 高，但脸太泛化、容易撞脸 | 备选 |
| 厚涂插画 | 单张最好看，20 镜下来脸一定漂 | 只适合少量特写 |
| 水墨淡彩 | 最差，跨镜视变脸 | 只做点缀 |

### 写实/电影感镜头的三个锚（不做漫画风时用）

漫画风靠画风统一；写实风靠「锚」压住 AI 味。三个锚缺一不可：

**① 用真实演员锚定气质，不要堆形容词。**
`Young Adrien Brody spirit, unglamorous` 比 `handsome, cinematic face` 有效十倍 —— 模型认识演员的脸，不认识「电影感」这两个字对它的含义。

**② 皮肤真实感清单（写实人像必带）。**
`Real skin texture: pores, peach fuzz, redness, capillaries, mild pigmentation` + `No airbrushing`。不写这两句，出来一定是塑料磨皮。

**③ 反 CGI 锚句（放在环境/场景提示词结尾）。**
英文：`no digital sharpness, no CGI look, imperfect analog texture, subtle film grain, soft halation`。
中文：用「不是 X，而是 Y」句式锁影调 ——「不是数字 HDR 式硬反差，而是胶片负片自然形成的柔和高反差」。
收尾再加一句决定成败的：

> 让画面像摄影机偶然捕捉的瞬间，而不是完整的游戏设定图。

这三句是「去 AI 味」的实际开关，比调 cfg／步数有用。中英混写分工：**中文管意向与逻辑，英文管技术参数**。道具图要预判模型会怎么错，提前写「不是两张分开的照片，而是同一张照片翻折着同时露出正反两面」。

完整画布级写法（`{{Mixed N}}` 参考图引用、「不参考绿幕背景」、分镜脚本的 ⚠️ 硬约束七条）见 skill `mv-production-ledger` 的画布侦查参考档（canvas-forensics）。

### 头身比和手：两个必踩的坑

1. **模型默认画成 Q 版大头。** 只写 `not chibi` 没用，要正面写 `realistic adult body proportions, seven and a half heads tall, natural leg length`，负面再加 `chibi, oversized head, tiny body, short legs`。
2. **手必畸形。** 最省事的解法是**让手不出现在画面里**：`hands in trouser pockets` / `hands not visible hidden behind` / `hands out of frame`。负面加 `claw hands, mutated hands, misaligned fingers`。

### 先查 /history，别从零拼 workflow

机器上已经跑通过这个模型，**正确的节点参数藏在历史里**，读出来比猜快十倍：

```bash
curl -s "http://127.0.0.1:8191/history?max_items=3"
```

读 `history[prompt_id]["prompt"][2]` —— 那是完整的 API 格式节点图，含模型名、采样参数、尺寸。任何你没装过的模型都先走这一步。

| 节点 | 关键参数 |

| `UNETLoader` | `unet_name=flux3-image-klein-int8-convrot.safetensors`, `weight_dtype=default` |
| `CLIPLoader` | `clip_name=qwen3vl_4b_int8_convrot.safetensors`, **`type="flux3"`** |

### prompt 写法

固定一个 STYLE 前缀给所有镜头，否则画风会散：

```
Chinese donghua comic illustration, thick rough ink outlines, rich gouache color painting,
hand-painted texture, cinematic rim light, heavy shadows, melancholic mood,
```

角色用固定描述串复用，**同一角色每一张贴完全同一串、一字不改**。串要具体到能被画出来：发色与发缝、黑眼圈、胡茬、脸型、上衣颜色、身体比例。例：

```
a tired 45-year-old Chinese man, short messy black hair with grey at the temples, stubble,
heavy dark circles under narrow eyes, round face, wearing the same dark grey short-sleeve
shirt, simple flat cartoon proportions with a slightly oversized head
```

写到这个颗粒度时，实测 4/4 张是同一人（脸型／发型／发色／胡茬／衣服全一致），**不需要再走 Qwen-Image-Edit 统一**。写成「一个中年男人」这种泛描述才会张张换脸。

负面词把不许出现的东西列全：

```
photo, 3d render, blurry, low quality, watermark, signature, extra fingers, deformed hands,
legible text, readable words, letters, numbers, document text, subtitles
```

### 画面里不要依赖可读文字

报纸、简历、书页、账单、屏幕上的字**必糊**，重出也糊。含文字的镜头改写成不靠文字表意：

- 「简历上年龄被红笔圈出」→ 红笔横在空白表格上、手悬着犹豫、浅景深
- 「翻开诗书看诗句」→ 俯拍旧书页、文字全部虚焦、一只年轻的手和一只老人手同时按在纸上
- 「酒桌旁的名片和收据」→ 只拍酒杯特写、背景虚化成 bokeh

### 验图：拼 contact sheet 一次看完

不要逐张调 `vision_analyze`（贵且慢）。用 PIL 拼 5 列网格（每格 320×468，角上标编号），一次问：

> 逐个检查：内容和编号意图是否匹配；有无畸形手／人脸崩坏／乱码文字／构图失败；画风是否统一。指出哪几张不能用。

只重出被判死刑的那几张。实测 17 张里会有 2~4 张因文字乱码需要重做，其余可用。

## 三、合成

### 逐段运镜（Ken Burns）

```bash
ffmpeg -y -loop 1 -i shot.png -t <dur> -vf \
"scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920,\
zoompan=z='min(zoom+0.00080,1.16)':x='iw/2-(iw/zoom/2)':y='ih/2-(ih/zoom/2)':d=<dur*30>:s=1080x1920:fps=30,\
format=yuv420p" \
-c:v libx264 -preset veryfast -crf 20 -r 30 seg.mp4
```

推：`z='min(zoom+0.00080,1.16)'`
拉：`z='if(eq(on,1),1.16,max(zoom-0.00080,1.0))'`

推、拉**在镜头之间交替**。全部同向会像 PPT。

**长镜头（>15 秒，尤其尾奏 30–40 秒）必须按总预算算步长，不能用固定增量。** `zoom+0.00X` 是**每帧**累加：`0.0025 × 30fps × 39s ≈ 2.9 倍`，画面被放大到只有原图中间一小块，直接糊成马赛克。上面那两个 `min()/max()` 写法之所以安全，就是因为有上限；自己写公式时：

```python
step = zoom_total / frames          # 比如 zoom_total=0.08、frames=1176 → 6.8e-5
z = f"min(1+{zoom_total:.6f},1+{step:.8f}*on)"
```

**尾奏/前奏这类无人声长镜，宁可只推 8–10%（0.08–0.10），也不要为了「有运动感」加大幅度。** 静帧推拉的作用是「不是死图」，不是真的运镜。

### 字幕用 ASS，不用 drawtext

多条字幕逐条 drawtext 会把滤镜链撑爆，中文字体路径、换行、描边都难控。写一个 `.ass` 文件一次烧录：

```
Style: Main,Noto Sans CJK SC,64,&H00FFFFFF,&H000000FF,&H00202020,&HA0000000,-1,0,0,0,100,100,2,0,1,3.5,2,2,70,70,210,1
Style: Title,Noto Serif CJK SC,96,&H00FFFFFF,&H000000FF,&H00101010,&H90000000,-1,0,0,0,100,100,6,0,1,4,3,5,60,60,0,1
```

`Noto Sans CJK SC` / `Noto Serif CJK SC` 在本机 `/usr/share/fonts/opentype/noto`。一句话拆两行用 `\N`，淡入淡出用 `{\fad(180,180)}`（片名卡用 `\fad(350,350)`）。

### 竖屏字幕安全区：MarginV 要按画面算，不要照搬别处的规范

**不要直接套其他项目现成的字幕规范。** 讲解类视频（白纸／浅底、人物在中部）那套参数搬到满屏插画 MV 上，字幕会正正压住主角的脸。实测：`MarginV 78`（距底 4%）压下巴，`280`（距底 15%）刚好贴边，`420`（距底 22%/字幕底边落在约 78% 高度）才干净。

原因：满屏插画的构图重心比白底讲解低，人物头部常落在 50%–80% 区间；而**抖音底部 UI（文案、音乐条）吃掉最后 10%–15%**。两条一夹，安全带只剩约 75%–80%。

竖屏 1080×1920 的可用起点（实测出片验证过）：

```
Style: Main,Noto Sans CJK SC,104,&H00FFFFFF,&H000000FF,&H00000000,&H64000000,-1,0,0,0,100,100,1.5,0,1,3.6,1.6,2,70,70,420,1
Style: Title,Noto Serif CJK SC,150,&H00FFFFFF,&H000000FF,&H00000000,&H78000000,-1,0,0,0,100,100,8,0,1,4.5,2.5,5,60,60,0,1
```

- `Fontsize 104` 在 1920 高画面上字面高约 72px；**64 号在这尺寸上太小**（那是 1080p 横屏或小画布的数值）
- 每行 ≤13 字：13 × 72px = 936px，1080 宽左右各留 72px
- `Alignment 2` + `MarginV` 才是底部居中；`Alignment 5` 是正中，别混
- 改 `MarginV` 用正则批量改 Style 行，**不要改 `PlayResX/Y`**（改了所有字号和边距按比例失真）

**前奏那 20 多秒不要空着** —— 先上片名卡，再上一句引子台词，把注意力钉住，等开唱再接正文。

### 720×1280 交付版的字幕参数（靠左贴边 + 柔光暗底）

用户对字幕的硬要求就三条：**整句一条一条**、**靠左贴边不居中**、**白字必须有暗底/描边**（“白字压在亮背景上不凸显”）。720×1280 成片的实测可用值：

```
Style: 影,LXGW WenKai,42,&H00000000,...,-1,0,0,0,100,100,2.1,0,1,2,2,1,68,201,462,1
Style: 词,LXGW WenKai,42,&H00FFFFFF,...,-1,0,0,0,100,100,2.1,0,1,2,2,1,68,201,462,1
```

- `Alignment=1`（左下角锚点）+ `MarginV 462` + `MarginL 68` → 实测字幕纵向落在 **61–63%**（抖音底部 25% UI 区之上）、左边距 **9–10%**
- **暗底用“两层同位置”实现，不是画矩形条**：影层黑字 + `{\blur11\bord3\shad0\alpha&H30&}`（柔光黑晕），词层白字 `bord2` 叠在上面；一条字幕输出两行 Dialogue（Layer 0 / Layer 1）
- 从数据表生成 ASS 时，**影层和词层必须同一对时间戳**，任何一边偏移都会出现“重影”
- 烧录：拼装滤镜最后一层挂 `subtitles='/绝对/路径.ass'`；用相对路径会因为 cwd 变化静默不烧

### 片头必须有歌名卡（0–3.4s），做法固定

用户会直接说「开幕的时候没有歌曲信息」。每集片头叠一张透明 PNG：楷体歌名 + 细横线 + 竖引线 + 三行职员小字（词曲 / 演唱 / 制作），压在开场的空镜上，0.15s 淡入、2.75s 起淡出。

- 生成：PIL 画 720×1280 RGBA（`/usr/share/fonts/truetype/comic-cn/LXGWWenKai-Regular.ttf`），歌名 78px 逐字加字距，整块落在画面 40% 高度左右
- 叠加：`-loop 1 -t 3.6 -i card.png` 取 `[2:v]format=rgba,fade=t=in:st=0.15:d=0.5:alpha=1,fade=t=out:st=2.75:d=0.6:alpha=1[tc]`，再 `[0:v][tc]overlay=0:0:enable='between(t,0.1,3.45)'`
- 验收：抽 1.7s 那帧，看歌名有没有压在背景高光上；小字只当氛围，不要求逐字读清

### 镜头表必须首尾相接，否则叠化错位

按歌词生成镜头表时，相邻镜常留 gap 或重叠。叠化链要求时间轴严格连续：**建表后立刻规范化**——重叠的截断上一镜、空档用上一镜补满、<0.3s 的镜并掉。不规范化时 `offset = 起点 − 0.24` 算出的位置与真实内容对不上，成片表现为叠化后画面比唱词晚半秒，逐段查还查不出来。

**验收时用像素量，不要问视觉模型位置百分比。** 实测 vision 把 61% 报成 86%（它看的是主体位置不是字幕行）。做法：抽帧转灰度 → 找下面 40% 区域里明显亮于均值的行 → 换回百分比，再报给用户。

### 字幕的形态与错落排版交给专用技能

三种出字形态（整句 / 逐字打字机 / 卡拉OK逐字高亮）、三锚点错落排版（有大有小、忽左忽右）、逐字/卡拉OK 的颜色语义（`PrimaryColour` = 已唱高亮、`SecondaryColour` = 未唱底）、ASS 参数与两个现成脚本，全部在技能 **`mv-subtitle-typography`**，不要在本技能里重推一遍。

**默认只能是① 整句一条一条，不要自己上逐字。** 用户会直接说「不要逐字显示，一条一条的显示」：逐字在静帧上看像「缺字」，连起来碎、费力；错落排版弄不好就是「乱」。想升档也得先出整句版交给用户看，他说“太规矩”再在个别金句上逐字——且一次只动一档，不要同时上逐字+错落+竖排。
脚本默认值已经是这个口径（`srt_to_ass_layout.py` 默认 `--pattern clean`，单锚点、整句、中下居中 100 号），**不要再去传参数“制造变化”**。
字幕目录里那份三形态对照表是描述能力边界，不是推荐用法——读它时先看本条。

### 没有官方 LRC 时（Suno `variety=4` 就是这种情况）：能量只能当校验器，不能当求句界的工具

流程：demucs 分轨 → **已知歌词强制对齐**（stable-ts `align`，只求时间不求识别）→ 用字级 token 拼句 → 用「发声率 + 字速」两项体检。四步的具体命令与脚本在 `mv-subtitle-typography` 的「五·D」。四条教训（都是花过几轮才弄对的）：

1. **对齐器遇到间奏会把一行从发声点一直拉到下一个发声点**（实测出现过 20 秒的行），所以必须有能量体检：发声率 <55% 或字速 <1.3 字/秒的行一律判为坏行。
2. **修坏行只做「收缩到该行所在的发声岛」，不要做「搬到时长匹配的岛」。** 后者会把 7 字句搬到 0.94 秒的短岛上、或者往前挪 3 秒；人是听得出差 2 秒的。
3. **不要在纯能量上做 DP 硬配**（“一行吃多段/多段分一行”的比例分摊）：连续演唱段在能量上是一整块，**段内没有静默可分**，句界只有 token/onset 知道；硬配的结果是全篇被均匀拉开（6 字行分到 12 秒），而且看起来“每一行都有时间”。
4. **交叉验证必做**：把同一人声轨 `transcribe()` 一遍，**只看时间戳不看字**（唱词必然错字，时间戳可信）。字幕与听写段偏差 >1.5s 的行，拿听写段 + 发声岛边界手工定一次；这类手工兜底通常只需动 1–2 行。

另：做「从第 N 秒起 25 秒」的验片时，`-ss` 放 `-i` 前面会重置时间戳，ASS 里的绝对时间事件全部落空 → **烧出一帧字幕都没有**。先把 ASS 时间整体减掉起点偏移写临时 ass 再烧。

两条本类任务踩过的验收坑：

1. **验字幕要把字烧到图上再抽帧，否则会误判“没渲染”。** 静图输入用 `ffmpeg -loop 1 -i bg.jpg -vf "subtitles=x.ass" -ss <秒> -frames:v 1 out.png` —— `-ss` 必须在**输出侧**。不给 -ss 或把它放输入侧，取到的永远是 t=0 那一帧（首句字幕往往 1 秒后才开始），几张预览图字节完全相同。
2. **判参考片的字幕排版，一帧不算数，抽到 10 帧以上再下结论。** 只抽 5 帧会得出“位置固定、只有一种字号”的错误结论；抽 12 帧才看得出真规律（前段小字右上、后段大字左侧竖排、换句才跳位）。要同时看两件事：同一句内是否锁死、换句时是否跳位。

### 拼接 + 混音 + 烧字幕

```bash
ffmpeg -y -f concat -safe 0 -i list.txt -i song.mp3 \
-vf "subtitles=sub.ass:fontsdir=/usr/share/fonts/opentype/noto,fade=t=in:st=0:d=1.2,fade=t=out:st=<dur-2.5>:d=2.5" \
-c:v libx264 -preset veryfast -crf 20 -pix_fmt yuv420p \
-c:a aac -b:a 192k -shortest -movflags +faststart out.mp4
```

各片段必须同分辨率／帧率／像素格式，否则 concat 出来的后半段会花屏。

### 帧数按累计时间算，不要逐段乘

每段帧数写成 `round((t1-t0)*30)` 会把每段的舍入误差累加起来 —— 实测 22 段拼下来总长少了 **2.76 秒**（163.70 vs 166.46），而且 `-shortest` 会把音频尾部悄悄切掉，参数完全看不出问题。

```python
f_start = int(round(t0 * FPS))      # 用绝对时间算起点帧
f_end   = int(round(t1 * FPS))
want_frames = f_end - f_start        # 差值就是这段该有的帧数
```

同时给每段 vf 尾部挂 `tpad=stop_mode=clone:stop_duration=2` —— 源片比目标帧数短时（模型按整数秒出片，请求 5.75 秒会拿到 6 秒或 5 秒，两个方向都会发生），不加 tpad 就截不够帧，加了也只是重复最后一帧，肉眼无感。

**装配后必须断言总帧数**：`round(目标时长 × FPS)` 与 `ffprobe` 实测差值应 ≤2 帧。差值上百帧就说明帧数算法有问题，别急着压手机版。

**如果要交给别人接手（而非自己交片），文档必须拆成两份，方向相反**：给执行者的是「怎么做 + 参数 + 验收清单 + 每个易错环节的错误/正确对比图」，给内部的是「踩过的坑 + 为什么这么选 + 效率真账」。写成一份两头不讨好。

用户对交接文档的硬要求是**「一定要有图有真相」**——只写文字等于没写，每个关键环节都要配视觉对照（终态效果图、多角度规范图、错误 vs 正确打标签对比图、实测抽帧图）。完整做法见 `ancient-rap-mv-production` 的「交付文档」一节。

1. `ffprobe` 确认 `width=1080 height=1920 r_frame_rate=30/1`，`duration` 与音频一致
2. 抽 4–6 帧拼一张图 `vision_analyze`，确认字幕真的烧上去、位置没被裁、无黑边拉伸。**关键：抽帧要故意选「人物在中下部」的那几秒**（近景、群像、坐着的人物）——人物在画面上半部的镜头看不出字幕压脸问题，抽了等于白验
3. **响度必须事后量一遍，不要信 `loudnorm` 的输入值。** 单遍 `loudnorm=I=-14` 实测出来是 −13.0 LUFS，改 `I=-14.5` 出来是 −13.5/峰值 −1.2 —— 单遍总是往目标上方偏 0.5～1 dB。做法：烧完跑一次测量（`-af loudnorm=print_format=summary -f null -`，看 `Input Integrated` / `Input True Peak`），落在目标 ±1 dB 内就收，**不要为了 0.5 dB 反复重编 45MB 的成片**
4. `MEDIA:<绝对路径>` 直接发视频，别只发路径
5. 同时把纯音频也发一份 —— 用户经常要先把歌单独发给别人听

## 口型：先量再改，别猜（2026-10-31 最终结论）

### 根因（实测，不是推测）
LibTV 出视频时 `params.enableSound:"on"` → **平台自己生成了一版音频**，嘴型跟着它自己那版走，与我们上传的母版人声不是同一轨。后果：
1. 每个 take 整体偏 **−5～−15 帧（最多 0.62s）**
2. 同一 take 内部还会漂（位移网格搜索 −20～+20 帧，conf 始终卡在 3.2–4.0）

→ **下一集开工第一件事：把 `enableSound` 关掉**，只让它按上传音频对口型。

### 必须先做的测量（`measure_final.py` 已写好，套用即可）
把成片拆成演唱段，每段配上**母版对应时间窗口的音频**，逐段跑 SyncNet：
```bash
/opt/lipsync-venv/bin/python eval/eval_sync_conf.py --video_path <段.mp4>   # 在 /opt/LatentSync 下跑
# 输出 SyncNet confidence + AV offset（帧）
```
offset 才是真指标（嘴型前后差几帧），conf 在“母版人声 vs 平台自生成音频”情况下会偏低，不能当唯一标准。

### 逐段补偿怎么做（`build_v10.py` + `每镜补偿.json`）
- `k` 帧为正值 = **跳过源素材前 k 帧**（内容提前）；负值 = 往前提源素材（内容推后）
- 素材前面没余量（local<0）→ 整段输出往后挪 k 帧，靠前一镜尾垫吸收
- 迭代公式：`k_new = k_old + 实测offset`，两轮就能从 −15 收到 0～±1

### 同时要守住的另外两条
- **不能用“互相关对齐音频”代替 SyncNet**：平台自生成音频与母版峰值只有 0.1–0.3，会锁到错的位置（`align_takes.py` 实测发散，已弃用）
- **调不动的段落直接拿情景照塞掉**（静帧 zoompan 成 0.6–3s 片段，不出脸就没有口型可错）。隔玻璃/大反光镜头基本无法对齐，一律用塞的

## 唱歌对口型：本地 LatentSync 用不了（2026-11-01 干净 A/B）

**测法很关键**：切一段成片，**驱动用的声音和评测用的声音必须是同一段母版人声**。之前拿切片音驱动、拿母版评，结论是错的。

| 片段 | 原始 conf / offset | LatentSync 后 conf / offset |
|---|---|---|
| V5a（副歌） | 0.59 / +14 | **0.23** / −15 |
| V7（全景） | 1.06 / −9 | **0.25** / 0 |

**offset 归零了，但 conf 掉到 0.2～0.3**：嘴和声音基本不相关。
根因：LatentSync / MuseTalk / Wav2Lip 全是**说话**语料训的，唱歌的长音、滑音、气声当异常输入，模型“糊嘴保平”。

所以唱歌 MV 只能走两条腿：
1. **剪辑层**：段级 offset 补偿 + 弱镜换素材/空镜（零氪，把 0±1 帧做对）
2. **付费 API**：可灵「对口型」**0.5 积分 / 5 秒**（≈¥0.1/秒；118 秒全片 ≈ 12 积分）；第三方 PiAPI $0.1/5s
3. 开工前先跑 **10 秒三臂 A/B**（原片 / LatentSync / 付费），过线才开整片

**可灵 lip-sync 实测（整片 10 段跑完的账）：** offset 一律收进 ±2 帧、conf 普遍 ×4–5（如 1.27→6.00、2.00→6.60），**但 10 段里有 2 段必须回滚** —— 数字好看的段也可能展屏后表情变僵：该闭嘴的捅开了、牙齿糊成白块、下颅轮廓被拉扯。

**所以规矩是两条，不是一条：**
1. 只送「脸大 + 一直在唱 + 偏移救不回」的段，不整片重做
2. **跑完必须逐段抽帧看脸（≥ 4 帧/段），数字过了也不一定能用** —— 只要那一段有表情停顿/抿嘴/低头，就默认它会被掰成张嘴上唱，直接准备回滚

回滚做法：把可灵版的段单独存目录，建工程时只替换合格那几段，不合格的段指向原素材（不要覆盖原文件，不然回滚时要重新切）。

## 花絮（BTS）必须逐张识图 + 按歌词对位（2026-10-31 血教训）

**症状**：花絮画面很好，但逻辑全错——水杯出现在「钥匙还给房东」那句，门后外套掉在间奏里。原因是按**文件名/空档**排的，没真实看图、没对歌词。

**铁律**：
1. 每条花絮先 `vision_analyze` 看一帧（`ffmpeg -ss 2 -frames:v 1`），把「画面里到底是什么物件」写成文字记下来
2. 把歌词逐句展开，标出每句的**具象锚点**（搬过七次家→行李箱；钥匙还给房东→门/锁；挂上外套→门后大衣；桌边喝水→杯子；半抽屉登机牌→抽屉票根；明信片撕掉→碎纸；走了那么远→托运标签；没拆过它→拉链）
3. 一物件只对一句，插在**那句唱完的瞬间**，不是插在随便一个空档
4. 一镜里有多句时，花絮只能放到该镜尾部——宁可放间奏，也不要错句

**技术上怎么插而不推后时间轴**：切片本身带 0.25s 前导 + 0.42s 尾垫。在某句结束处把镜头劈成 a/b，插 0.4s 花絮，再从 **b 段尾部吃掉 0.4s 垫片** —— 内容起点、唱词位置、总时长全部不变。见 `build_v7.py`。

**验证**：每个插入点抽一帧，vision 只问「这是什么物件」+ 用 ASS 事件时间核对当前字幕是哪句；两者对上才算过。

**自动推荐插入点：素材标签索引 + 模糊锚点匹配**（把上面的人工判断固化成可复用的表）

- 每张素材落一组**标签**（不是描述）：行李箱→`行李箱 箱子 搬家 胶带`，抽屉→`抽屉 票根 登机牌 房卡`，门→`门 锁 钥匙 房东`，空棚→`空棚 房间 环境`
- 每句歌词落一组**锚点词**，按锚点∩标签打分排序，取前 3 张
- **匹配必须是模糊的**：ASR 出来的歌词一定错字（实测「你攒了半抽屉登机牌」被听成「你藏了半抽屉等几排」），精确包含匹配会返回空。用最长公共子串（`difflib.SequenceMatcher.find_longest_match`）与锚点句比，长度 ≥2 就采纳，否则退回关键词包含
- 建议只给候选，用户点哪张插哪张；不要自动插入——语义对位这种判断错了就是整条重排

## 口型与拼装：2026-10-31 实测补丁（一个镜一个镜量出来的）

### 用 SyncNet 打分，不要用眼睛验收口型

```bash
cd /opt/LatentSync && CUDA_VISIBLE_DEVICES=0 HF_HUB_OFFLINE=1 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
  PYTHONPATH=/opt/LatentSync env -u VIRTUAL_ENV -u PYTHONHOME /opt/lipsync-venv/bin/python \
  eval/eval_sync_conf.py --video_path <绝对路径.mp4>
# SyncNet confidence（≥6 算好） / AV offset（±1 帧可接受）
```
需先 `pip install "scenedetect==0.6.4"`（新版无 `video_manager`）；环境变量漏一个就报 `ModuleNotFoundError: eval` 或 OOM。

### LatentSync 整片替换会大幅降分（实测 9/10 镜变差）

star-video2.5 原片 vs LatentSync 重做嘴：V1 5.70→**6.36**（只有这一镜提分），V2 3.29→2.10、V5 4.33→2.79、V6 6.48→5.14、V7 5.27→3.19、V8 3.82→1.73。偏移能修到 0 帧，但置信度掉 —— 它把嘴做糊，观众感知是「在动但不像在唱」。
**铁律：逐镜 A/B，只采用分数更高那版，绝不整片替换。** 隔玻璃/反光镜头会直接 `Face not detected`（整段检不到脸，不是逐帧跳过）。

### 移轴的边界：时间能修，字修不了

- 时间轴偏移 1–2 帧内可修（SyncNet offset 0±1 可达）
- 字级唇形修不了：188 个字逐字测 lag，实测 −8 到 +8 帧随机跳 → 模型没按字发音，移轴只会拆东墙补西墙
- 弱镜（conf <4.5）**重抽比移轴有用**：同镜换 seed + 提示词加「双唇闭合的字真闭唇、咧嘴的字横向拉开、圆唇的字收圆」，实测 V2 3.29→4.39、V8 3.82→4.23；V5 抽两条都更差就保留原片

### 叠化会把画面整体推后（这是「一开口就没对上」的真因）

`xfade` + `tpad` 头部垫片会让内容延后（垫 0.42s 就晚 10 帧）。正解：
- 叠化**结束点 = 该段内容起点**：`offset = 该段绝对起点 - trans`
- 头垫只垫 `trans`，尾垫吃 gap
- 位置一律用**绝对时间轴**算，不要累积长度

### 冻结帧填缝会被用户判成「跳帧不平顺」

镜头之间用冻结帧顶空档，用户一眼看出卡住。改成**花絮插图桥**：从花絮视频中段截 0.5–1.1s **真实运动**片段（不是静帧 zoompan，静帧在 1s 插格里会被当成卡帧），两侧各 0.3s 叠化。

### 前奏长度是硬需求，不是审美

15.3s 前奏会被打回（「前奏太长，还是一样」）。做法：`0–4.0s + 12.8s 起`，`acrossfade d=0.4` 接起来，前奏压到 6.3s；**字幕整体平移 9.2s**（= CUT_B − CUT_A + XF），片头字卡 3s + 空棚 3.3s 就进人。

### 混分辨率拼不起来

duration 一半 1080p 一半 720p 时 `xfade` 直接报错退出。拼装前每段先 `scale=720:1280:force_original_aspect_ratio=decrease,pad=720:1280`，成片统一 720×1280。

## Pitfalls

1. **批量提交的计数不要用剩余字典长度。** `while done < len(pending)` 配上 `pending.pop()` 会在一半时提前退出（`done` 在涨、`len` 在跌），任务其实还在队列里没人收，表现为「只回来 10/17」。用单独的 `total` 常量判断。
2. **跨镜头换脸是角色描述写太泛的后果，不是默认结果。** 串里写清发缝／黑眼圈／胡茬／衣服颜色／身体比例时，实测四张全是同一人；只有写成「一个中年男人」才会张张脸不同。先补具体描述重出那一张，仍不一致才上 Qwen-Image-Edit 拿正面图当参考批量改 —— 别跳过第一步直接上 Edit。
3. **不要加步数**：flux3 klein 是蒸馏模型，`cfg=1.0` + 26 步就是它的设计点，加步数只涨时间不涨质量。
4. **先确认音频定了再做画面。** 歌词小改不影响已出的图，但换歌或改时长会让整条时间轴作废。词没定稿就只出图、不合成。
5. **纯器乐前奏对短视频是硬伤**，别等成片才发现。拿时间轴第一步就看 `segments[0].end`。
6. **装配时必须断言「实际用上几个素材」，否则会静默出片。** 镜头文件按计算出的名字（`{tag}_{秒数}_lip.mp4`）去取时，名字对不上就只是返回「不存在」，然后装配逻辑平静地回退到默认运镜 —— 成片时长、分辨率、字幕全部正常，只是**所有对口型镜头一个都没用上**，而你看参数完全看不出问题。原因是文件名里的秒数用了段内相对时间，查找时却用了全片绝对时间。

   两条防御：

   - 装配开头**分类打印实际命中数**：`对口型镜头可用 N 个 / 预期 M 个`，N=0 立刻停。这一行比任何参数校验都有用。
   - 段内相对时间和全片绝对时间**在同一个结构里同时存**（`(tag, 绝对起点, 时长, 文件名相对秒数)`），不要靠推算去还原另一个。

   交付前回想一句：这个镜头的效果，我是在**成片里**看到的，还是在源素材里看到的？只在源素材验过就等于没验。

7. **`bare-headed` 会被出图模型理解成「光头」，不是「没戴帽子」。** 想让主角不戴安全帽但保留头发时，写 `short black hair visible, no hard hat`。写成 `bare-headed` 会直接给他剃光 —— 而且这个错误在一帧里就能产生，下一镜又有头发，跨镜身份直接崩。不戴帽就要**正面写头发**，不要靠「bare」这类否定词。

8. **ComfyUI `LoadImage` 的 `image` 字段必须带扩展名。** 写 `vB` 应为 `vB.png`，否则报 `prompt_outputs_failed_validation` / `custom_validation_failed`，错误信息不会告诉你缺的是扩展名。宁可把参考图复制成固定名字（`va.png` / `vb.png`）再引用，也别传不带后缀的名。

9. **静帧推拉（Ken Burns）的锐度要用 unsharp 拉回。** 纯 `scale` 放大后锐度会明显下降（实测 2.9 → 1.3）；加 `unsharp=5:5:1.2:5:5:0.4` 能回到 2.8，`5:5:2.0` 能拉到 3.3（比原图还清一点且不过度）。不只是一两秒的空镜 —— 唇同步输出从 512 放到 1080 时也必须走同一道锐化。

   **不要试图用 4x 超分去救清晰度。** 超分再 lanczos 缩回原尺寸，补出来的细节被重新抹平，实测超分前后锐度不升反降（4.8 → 4.3）。**目标尺寸不变时超分是白做** —— 1080×1920 本来就是竖屏发布标准尺寸，缺的是锐度不是像素，用 unsharp 就够。

10. **「本机能不能出视频」先算显存账，不要先调参。** 14B 双模型 i2v（WAN2.2 high+low 各 14G）参数总量 28G，单张 24G 卡装不下就必然在 CPU↔GPU 之间反复搬权重，fp8 精度被反复截断，**结果是脸从第 2 秒开始变形、画面块状马赛克**。这是带宽问题，不是步数或分辨率能救的：实测 480p/10 步打 4 分，提到 720p/30 步反而打 2 分（越清晰越暴露崩坏）。

    **诊断信号：`nvidia-smi` 显存吃到 19G 但利用率 0% = 在搬权重不是真在算；100% 才是真算。** 看到「占满显存却 0% 利用率」就不要等，直接判定这条模型/分辨率组合在本机不可用。要么换 14G 级单模型（单模型才塞得进 24G，不走 offload），要么走云端。完整实测矩阵见 `references/本地视频模型能力判据.md`。

11. **唇同步（Sonic）的 `frames_per_batch` 太大会死锁，不是慢。** 实测 `frames_per_batch=25`：模型加载完成后就不进入计算，队列显示 running、GPU 只占约 2G、利用率 0%，十几分钟零输出。**改成 8 立刻通**（512 分辨率、8 秒素材约 200 秒出片）。另两条硬约束：`dtype` 只能 `fp16`（权重固定 fp16，写 `bf16` 报 `mat1 and mat2 must have the same dtype, but got Half and BFloat16`）；768 分辨率 OOM，只能 512。

    **通用判据：任何「提交成功但 GPU 不动」的生成任务，先查 batch／分块类参数，不要靠等超时。** 超时报出来的「失败」会掩盖真正的参数病因。

12. **改构建脚本用 `patch` 工具，不要用 Python 切片替换（`s[s.index(锚点):s.index(锚点2)]`）。** 锚点串在文件里往往出现多次（函数体、注释、日志各一份），`index()` 取第一个、终点落到错位置，一次替换就能把两千行的脚本膨胀成十几万行重复内容，**而且当场不报错**——直到下次跑 ffmpeg 才发现参数全乱。判据：改完先 `wc -l` 对一下原行数，翻倍就是改坏了；坏了就把文件 `mv` 走整个重写，不要在坏文件上继续打补丁。同理，`write_file` 拒写已存在文件时，先 `mv` 走再写，不要硬覆盖。
